# 공통 감사필드와 계좌계 엔티티 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 DDL로 설계한 테이블 구조를 Spring Boot와 JPA 코드 구조로 옮기기 시작하는 것이다.
이번 단계에서는 모든 엔티티를 한 번에 만들지 않고, 계좌계에서 가장 먼저 필요한 공통 기반과 핵심 엔티티를 우선 작성했다.

이번에 만든 범위는 아래와 같다.

- 공통 감사 필드
- 금액 타입
- 고객 엔티티
- 상품 엔티티
- 계좌 엔티티
- 계좌 소유 관계 엔티티
- 계좌 현재 잔액 엔티티

## 2. 왜 공통 감사필드가 먼저 필요한가

거의 모든 주요 테이블에는 `created_at`, `updated_at` 같은 공통 필드가 들어간다.
이것을 엔티티마다 반복해서 작성하면 중복이 많아지고, 나중에 규칙을 바꾸기 어려워진다.

그래서 `common` 모듈에 `BaseEntity` 를 만들고, 모든 엔티티가 이 클래스를 상속하도록 했다.

이번 `BaseEntity` 의 역할은 다음과 같다.

- 생성 시각 자동 기록
- 수정 시각 자동 기록
- 엔티티마다 같은 컬럼 정의를 반복하지 않기

## 3. 왜 금액 타입이 필요한가

코어 뱅킹에서는 금액을 단순 숫자로만 다루기 시작하면 나중에 오류가 나기 쉽다.
예를 들면 아래 문제가 생길 수 있다.

- 통화가 다른 금액을 더하는 문제
- 소수점 자릿수가 일관되지 않은 문제
- 금액 비교 로직이 흩어지는 문제

그래서 `Money` 타입을 공통 모듈에 만들었다.
이번 단계에서는 아직 JPA 컬럼에 직접 매핑하지는 않았고, 도메인과 서비스 로직에서 사용할 수 있는 공통 값 객체로 먼저 준비했다.

즉, 지금은 `BigDecimal` 기반 DDL과 JPA 매핑을 우선 맞추고, 도메인 코드에서 금액을 더 안전하게 다룰 수 있는 기반을 마련한 것이다.

## 4. 이번에 만든 계좌계 엔티티

### 4.1 `Customer`

고객 기준 데이터를 표현하는 엔티티다.

주요 필드:

- 고객 번호
- 고객 유형
- 이름
- 상태

이 엔티티가 필요한 이유는 계좌와 거래가 모두 결국 고객과 연결되기 때문이다.

### 4.2 `Product`

상품 기준 데이터를 표현하는 엔티티다.

주요 필드:

- 상품 코드
- 상품명
- 상품 유형
- 상태

이 엔티티는 계좌가 어떤 상품에 속하는지 표현하는 기준점이다.

### 4.3 `Account`

계좌 기준 데이터를 표현하는 엔티티다.

주요 필드:

- 계좌 번호
- 상품
- 통화 코드
- 상태
- 개설 시각
- 해지 시각

또한 `Account` 는 아래와 관계를 가진다.

- 상품과는 다대일
- 계좌 잔액과는 일대일
- 계좌 소유 관계와는 일대다

### 4.4 `AccountHolder`

고객과 계좌의 관계를 표현하는 엔티티다.

왜 필요한가:

- 한 고객이 여러 계좌를 가질 수 있다.
- 한 계좌가 공동명의일 수도 있다.
- 단순히 `account` 에 `customer_id` 하나만 두면 확장이 어렵다.

그래서 고객과 계좌 사이를 `AccountHolder` 로 풀었다.

### 4.5 `AccountBalance`

계좌의 현재 상태를 표현하는 엔티티다.

주요 필드:

- 원장 잔액
- 출금 가능 잔액
- 보류 금액
- 마지막 거래 식별자
- 버전

이 엔티티를 `Account` 와 분리한 이유는 다음과 같다.

- 잔액은 매우 자주 바뀌는 데이터다.
- 락과 버전 관리가 필요하다.
- 계좌 기준 데이터와 현재 상태 데이터는 성격이 다르다.

## 5. 왜 enum 을 같이 만들었는가

이번 단계에서는 아래 enum 들도 같이 만들었다.

- `CustomerType`
- `CustomerStatus`
- `ProductType`
- `RecordStatus`
- `AccountStatus`
- `AccountHolderRole`

이유는 상태값과 유형값을 문자열로 아무렇게나 쓰기 시작하면 오타와 규칙 불일치가 생기기 쉽기 때문이다.

enum 을 쓰면 다음 장점이 있다.

- 가능한 값의 범위를 코드에서 제한할 수 있다.
- 의미를 더 쉽게 읽을 수 있다.
- 나중에 검증 로직을 넣기 쉽다.

## 6. JPA 관점에서 이번 구조를 어떻게 봐야 하는가

### 6.1 `@Entity`

이 클래스가 DB 테이블과 연결되는 JPA 엔티티라는 뜻이다.

### 6.2 `@Table`

실제 어떤 테이블명과 연결되는지 지정한다.

### 6.3 `@Id`

기본 키를 뜻한다.

### 6.4 `@ManyToOne`, `@OneToOne`, `@OneToMany`

엔티티 사이의 관계를 표현한다.

이번 작업에서는 아래 관계를 코드로 표현했다.

- 상품 하나에 여러 계좌
- 계좌 하나에 하나의 현재 잔액
- 계좌 하나에 여러 계좌 소유 관계
- 고객 하나에 여러 계좌 소유 관계

### 6.5 `@MapsId`

`AccountBalance` 에서 사용했다.
이것은 `account_balance.account_id` 가 PK 이면서 동시에 `account.account_id` 를 참조하는 FK 라는 뜻이다.

즉, 계좌 잔액은 독립적인 식별자를 새로 가지지 않고 계좌 식별자를 그대로 사용한다.

### 6.6 `@Version`

잔액 엔티티의 `version` 필드에 사용했다.
이 값은 낙관적 락에 사용된다.

의미는 다음과 같다.

- 동시에 두 요청이 같은 잔액을 수정하려고 할 때 충돌을 감지할 수 있다.
- 나중에 이체 로직에서 동시성 제어의 기본 장치가 된다.

## 7. MVC와 지금 만든 코드의 관계

이번에 만든 엔티티들은 MVC 중에서 주로 모델에 해당한다.
정확히는 단순 MVC 모델보다 도메인 모델에 더 가깝다.

즉, 아직은:

- Controller 없음
- Service 없음
- Repository 없음
- Entity 중심의 도메인 모델만 생성

상태다.

이 순서가 중요한 이유는, 먼저 모델이 있어야 그 위에 저장소와 서비스가 자연스럽게 올라가기 때문이다.

## 8. 이번 단계에서 일부러 아직 하지 않은 것

이번에는 아래 내용은 아직 넣지 않았다.

- Repository 인터페이스
- DTO
- Controller
- 입금, 출금, 이체 서비스
- 거래 원장 엔티티

이유는 먼저 계좌계 기준 데이터를 안정적으로 코드로 옮기는 것이 우선이기 때문이다.
