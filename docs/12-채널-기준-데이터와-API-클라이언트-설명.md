# 채널 기준 데이터와 API 클라이언트 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 이전 단계에서 임시로 넣어 둔 `channelId = 1` 같은 하드코딩을 제거하고, 채널과 API 클라이언트를 `기준 데이터` 로 다루는 구조를 만드는 것이다.

이전 단계에서는 API 요청 이력을 남기기 위해 아래 정보를 저장했다.

- 어떤 채널로 들어온 요청인가
- 어떤 API 클라이언트가 보냈는가

하지만 실제 코드는 아래처럼 임시 상태였다.

- 채널은 `OPEN_API_CHANNEL_ID = 1` 로 고정
- API 클라이언트는 아직 연결되지 않음

이 방식은 학습 단계에서 빠르게 시작하기에는 편하지만, 구조적으로는 오래 유지하면 안 되는 상태다.

그래서 이번에는 아래를 목표로 작업했다.

1. `channel` 테이블을 코드의 기준 데이터로 연결
2. `api_client` 테이블을 코드의 기준 데이터로 연결
3. 요청 이력 저장 시 채널과 API 클라이언트를 조회해서 연결
4. 이후 인증 구조를 붙일 수 있는 자리 만들기

## 2. 왜 이 작업이 지금 필요한가

### 2.1 하드코딩은 설계를 약하게 만들기 때문이다

`channelId = 1` 같은 상수는 처음에는 간단해 보인다.
하지만 시스템이 조금만 커져도 아래 문제가 생긴다.

- 실제 DB 데이터가 바뀌면 코드도 같이 바꿔야 함
- 개발/테스트/운영 환경마다 ID 값이 다를 수 있음
- "왜 1인가" 를 코드만 보고는 설명하기 어려움
- 새로운 채널이 추가되면 if, constant, 하드코딩이 늘어남

즉, 채널은 숫자 ID 자체가 중요한 것이 아니라 `OPEN_API` 라는 업무 의미가 중요하다.

그래서 코드는 보통 아래 방향으로 가야 한다.

- 코드: `OPEN_API` 같은 업무 코드 사용
- DB: 실제 PK 는 내부 식별자 역할

이게 기준 데이터 설계의 핵심 중 하나다.

### 2.2 채널과 API 클라이언트는 업무 기준 정보이기 때문이다

`channel` 과 `api_client` 는 거래 이력처럼 계속 쌓이는 데이터가 아니다.
이들은 다른 데이터가 참조하는 기준점이다.

즉, 이 두 테이블은 다음 성격을 가진다.

- 자주 변하지 않음
- 다른 이력 데이터가 참조함
- 코드로 직접 박아 넣기보다 DB 기준 데이터로 관리해야 함

이전 상위 설계에서 정리한 `기준 데이터`, `상태 데이터`, `이력 데이터` 관점으로 보면:

- `channel`, `api_client` 는 기준 데이터
- `api_request_log` 는 이력 데이터

이 관계를 실제 코드에도 반영해야 구조가 일관된다.

### 2.3 인증을 붙이기 전에 식별 구조부터 분리하는 것이 좋기 때문이다

이번 단계는 아직 `인증(authentication)` 을 구현한 것은 아니다.
대신 `식별(identification)` 의 기초를 만든 단계다.

두 개념은 다르다.

- 식별: "이 요청은 누구라고 주장하는가"
- 인증: "그 주장이 সত্য인지 검증하는가"

이번에는 `X-Api-Client-Key` 라는 헤더를 읽어 API 클라이언트를 찾는 구조만 만들었다.
이것만으로는 보안적으로 충분하지 않다.

하지만 구조적으로는 매우 중요하다.
왜냐하면 나중에 인증을 붙일 때도 결국 "어떤 클라이언트를 검증할 것인가" 를 알아야 하기 때문이다.

즉, 지금 단계는 보안 완성이 아니라 `보안 구조의 첫 기준점` 이다.

## 3. 이번에 만든 구조의 큰 흐름

이번 작업 이후 API 요청 이력 저장 흐름은 아래처럼 바뀌었다.

1. 요청이 들어온다.
2. `ApiRequestLoggingInterceptor` 가 요청 종료 시점에 동작한다.
3. 인터셉터는 `OPEN_API` 채널 코드와 `X-Api-Client-Key` 헤더를 읽는다.
4. `ChannelIdentityResolver` 가 DB에서 채널과 API 클라이언트를 조회한다.
5. 조회한 `channelId`, `apiClientId` 를 `api_request_log` 저장에 사용한다.

즉, 이제 요청 이력은 더 이상 "1번 채널" 같은 하드코딩 숫자에 의존하지 않고, 실제 기준 데이터 조회를 통해 연결된다.

## 4. 왜 channel-security 모듈에 두었는가

이 부분은 구조 학습 관점에서 중요하다.

### 4.1 channel-api 는 요청 진입과 응답에 집중해야 한다

`channel-api` 모듈의 주 책임은 아래와 같다.

- HTTP 요청 받기
- DTO 검증
- 응답 변환
- 공통 웹 처리

반면 채널 기준 데이터나 API 클라이언트 식별은 단순 웹 처리보다 `채널 보안/식별 영역` 에 더 가깝다.

그래서 이 책임은 `channel-security` 로 분리하는 편이 구조적으로 자연스럽다.

### 4.2 이후 인증/인가가 붙을 자리를 미리 마련하기 위해서다

지금 `channel-security` 모듈은 거의 비어 있었다.
이번 단계에서 아래를 먼저 채워 넣었다.

- 채널 기준 데이터 모델
- API 클라이언트 기준 데이터 모델
- 채널/클라이언트 식별 리졸버

그러면 다음 단계에서 아래를 붙이기 쉬워진다.

- API 키 검증
- 클라이언트 상태 검증
- 채널별 접근 정책
- Spring Security 필터 체인

즉, 이번 작업은 단순 데이터 모델링이 아니라 `보안 모듈의 실질적 시작점` 이다.

## 5. 이번에 만든 주요 코드와 역할

## 5.1 `Channel`

역할:

- `channel` 테이블과 매핑되는 기준 데이터 엔티티

포함 정보:

- `channelCode`
- `channelName`
- `channelType`
- `status`

왜 중요한가:

- 채널을 숫자 ID 가 아니라 업무 의미가 있는 코드로 다룰 수 있게 해 준다.

## 5.2 `ApiClient`

역할:

- `api_client` 테이블과 매핑되는 기준 데이터 엔티티

포함 정보:

- 소속 채널
- `clientKey`
- `clientName`
- `status`

왜 중요한가:

- 이후 외부 호출 주체를 채널과 연결된 단위로 식별할 수 있게 해 준다.

## 5.3 `ChannelRepository`, `ApiClientRepository`

역할:

- 채널 코드와 클라이언트 키로 기준 데이터를 조회한다.

의미:

- 기준 데이터 조회 책임을 도메인 관점 인터페이스로 분리했다.
- `channel-api` 는 저장소 구현 방식을 몰라도 된다.

## 5.4 `ChannelIdentityResolver`

역할:

- 채널 코드와 클라이언트 키를 받아 `channelId`, `apiClientId` 를 계산한다.

왜 따로 뺐는가:

- 인터셉터가 직접 저장소 두 개를 조합하면 웹 계층 코드가 두꺼워진다.
- 식별 규칙이 바뀔 때 한 곳에서 수정할 수 있게 하기 위해서다.

이 클래스가 하는 판단은 아래와 같다.

1. 채널 코드로 활성 채널을 찾는다.
2. 없으면 예외를 던진다.
3. 클라이언트 키가 있으면 활성 API 클라이언트를 찾는다.
4. 찾은 클라이언트가 같은 채널 소속인지 확인한다.
5. 맞으면 `apiClientId` 를 반환하고, 아니면 `null` 로 둔다.

여기서 중요한 점은 `채널은 필수`, `API 클라이언트는 현재 단계에서 선택적` 으로 본다는 것이다.

이유는 다음과 같다.

- 채널 정보는 요청 이력 저장에 반드시 필요하다.
- API 클라이언트는 아직 인증 구조가 없기 때문에, 지금 단계에서는 없거나 맞지 않아도 요청 전체를 깨지 않게 설계했다.

## 5.5 `X-Api-Client-Key` 헤더 추가

이번에 `ChannelApiConstants` 에 `X-Api-Client-Key` 헤더 상수를 추가했다.

의미:

- 외부 호출 주체를 식별하기 위한 채널계 입력값을 명시적으로 받기 시작했다.

주의:

- 이 헤더를 받는다고 해서 인증이 끝난 것은 아니다.
- 현재는 `식별용 입력값` 이다.

## 6. 왜 API 클라이언트 조회는 엄격하고도 느슨하게 설계했는가

이 표현이 조금 이상하게 들릴 수 있지만, 실제로는 두 가지 균형이 필요했다.

### 6.1 채널은 엄격하게 본다

활성 채널이 없으면 예외를 던진다.
이유는 채널이 없으면 요청 이력의 기본 축 자체가 무너지기 때문이다.

즉:

- 어떤 요청이 어떤 채널로 들어왔는지 모르면
- 채널계 로그의 기준점이 사라진다.

### 6.2 API 클라이언트는 현재 단계에서는 느슨하게 본다

클라이언트 키가 없거나, DB에 없거나, 채널이 맞지 않으면 `apiClientId = null` 로 둔다.

이렇게 한 이유는 다음과 같다.

- 아직 인증 구조가 완성되지 않았음
- 지금 단계의 우선순위는 요청 이력의 기본 뼈대를 세우는 것임
- 모든 외부 호출을 즉시 차단하는 것은 아직 설계 범위를 넘음

즉, 현재는 `실패시키는 식별` 보다 `쌓아 두는 식별` 에 가깝다.
다음 단계에서 인증을 붙이면 이 정책은 더 엄격해질 수 있다.

## 7. 왜 시드 SQL 파일도 같이 만들었는가

이번에 [V2__channel_reference_data.sql](C:\SSAFY\joseph\workspaces\BankingSystem\database\ddl\V2__channel_reference_data.sql) 을 추가했다.

이 파일의 역할은 다음과 같다.

- `OPEN_API` 채널 기준 데이터 준비
- 기본 오픈 API 클라이언트 기준 데이터 준비

왜 필요한가:

- 코드가 기준 데이터를 조회하도록 바뀌었기 때문에, 실제 DB에도 최소 기준 데이터가 있어야 한다.
- 그렇지 않으면 런타임에서 채널 조회가 실패한다.

즉, 기준 데이터를 코드로 연결했다면 `DB에 그 기준이 실제로 존재하는가` 도 같이 관리해야 한다.

이건 백엔드 학습에서 매우 중요한 포인트다.

- 엔티티만 만든다고 끝이 아님
- 그 엔티티가 참조할 기준 데이터의 초기 상태도 함께 설계해야 함

## 8. 테스트는 무엇을 검증했는가

이번에는 `ChannelIdentityResolverTest` 를 추가했다.

검증한 내용:

- 활성 채널과 활성 클라이언트가 있으면 둘 다 반환
- 클라이언트 키가 없어도 채널만 반환
- 활성 채널이 없으면 예외 발생

이 테스트가 중요한 이유는 `식별 규칙` 이 단순 조회처럼 보이지만 실제로는 정책 판단을 포함하기 때문이다.

즉, 이 코드는 단순 CRUD 가 아니라 아래 판단을 한다.

- 활성 상태인가
- 같은 채널 소속인가
- 필수 정보와 선택 정보를 어떻게 구분할 것인가

이런 정책 코드는 테스트가 있어야 다음 단계에서 안전하게 확장할 수 있다.

## 9. 이번 단계에서 얻은 구조적 이점

이번 작업 이후 아래 개선이 생겼다.

- API 요청 이력이 더 이상 하드코딩된 채널 ID 에 의존하지 않는다.
- 채널과 API 클라이언트가 실제 기준 데이터로 연결된다.
- `channel-security` 모듈이 실제 책임을 가지기 시작했다.
- 이후 인증/인가 구조를 붙일 준비가 되었다.
- 기준 데이터와 이력 데이터의 관계가 코드에 더 분명히 드러난다.

## 10. 현재 단계의 한계

이번 작업은 아직 완성형 보안 구조는 아니다.

### 10.1 `X-Api-Client-Key` 는 아직 검증 헤더가 아니다

현재는 식별에만 사용한다.
즉, 누군가 헤더를 보내면 그 값을 읽는 수준이다.

향후에는 아래가 필요하다.

- 서명 검증
- API Secret 또는 토큰 검증
- 키 만료 처리
- 클라이언트별 권한 정책

### 10.2 클라이언트 미일치 시 요청 자체를 막지는 않는다

현재는 `apiClientId` 를 비워 두고 로그를 남기는 방향이다.
이것도 다음 단계에서는 더 엄격하게 바꿀 수 있다.

### 10.3 기준 데이터 운영 관리 화면이나 배치가 아직 없다

지금은 SQL 시드 파일 중심이다.
추후에는 운영자 관리, 배포 시드, 마이그레이션 관리가 더 체계화되어야 한다.

## 11. 학습 포인트

- PK 숫자보다 업무 코드가 기준 데이터 연결에 더 안정적이다.
- 기준 데이터는 이력 데이터가 참조하는 축이므로 코드에서도 별도 모델로 다루는 것이 좋다.
- 식별과 인증은 다르며, 구조상 식별부터 분리해 두면 다음 단계 확장이 쉬워진다.
- 웹 계층에서 기준 데이터 조회 정책을 직접 쓰기보다 별도 리졸버로 빼는 편이 읽기 쉽고 테스트하기 좋다.
- 기준 데이터를 참조하는 기능을 만들면 초기 시드 데이터 관리도 함께 설계해야 한다.

## 12. 다음 작업 후보

이제 가장 자연스러운 다음 작업은 아래 중 하나다.

1. `X-Api-Client-Key` 기반의 실제 인증 검증 추가

3. 클라이언트 상태가 비활성이면 요청을 차단하는 정책 추가
