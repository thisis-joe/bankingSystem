# 스프링부트 멀티모듈 뼈대 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 코어 뱅킹 아키텍처와 핵심 테이블 DDL 초안을 실제 백엔드 프로젝트 구조로 옮길 수 있도록 Spring Boot 멀티모듈 뼈대를 만드는 것이다.

이번 단계에서는 아직 업무 로직을 구현하지 않는다.
대신 앞으로 코드를 어디에 둘지, 어떤 모듈이 어떤 책임을 가질지, 루트 빌드 파일은 어떤 역할을 하는지를 먼저 고정한다.

## 2. 왜 멀티모듈이 필요한가

코어 뱅킹은 기능이 많아질수록 코드가 쉽게 섞인다.
특히 아래 항목들이 분리되지 않으면 나중에 구조가 무너지기 쉽다.

- 공통 코드
- 계좌 도메인
- 거래 원장
- 이체 로직
- 이자 로직
- 외부 API 진입점
- 보안
- 조회 전용 기능
- 배치 작업

그래서 이번에는 처음부터 멀티모듈 구조로 분리했다.
다만 마이크로서비스가 아니라 하나의 프로젝트 안에서 모듈만 분리한 구조다.

## 3. 이번에 만든 루트 파일

### 3.1 `settings.gradle`

이 파일은 Gradle에게 어떤 하위 모듈이 있는지 알려준다.
즉, 프로젝트 전체 구성도를 선언하는 파일이다.

이번에 포함한 모듈은 아래와 같다.

- `common`
- `account-domain`
- `transaction-domain`
- `transfer-domain`
- `interest-domain`
- `channel-api`
- `channel-security`
- `information-read`
- `batch`
- `bootstrap`

### 3.2 `build.gradle`

이 파일은 루트 빌드 설정이다.
모든 하위 모듈이 공통으로 따라야 하는 규칙을 넣었다.

예를 들면 아래 내용이 들어 있다.

- Maven Central 저장소 사용
- Java 21 toolchain 사용
- Spring Boot 의존성 BOM 통일
- 테스트 시 JUnit Platform 사용

즉, 하위 모듈마다 같은 설정을 반복하지 않도록 루트에서 공통 규칙을 모아둔 것이다.

### 3.3 `gradle.properties`

이 파일은 버전과 공통 값을 모아두는 곳이다.

이번에는 아래 값을 넣었다.

- 그룹명
- 프로젝트 버전
- Java 버전
- Spring Boot 버전
- 의존성 관리 플러그인 버전

이렇게 하면 나중에 버전을 바꿀 때 한 곳만 수정하면 된다.

### 3.4 `.gitignore`

빌드 결과물, IDE 설정 파일처럼 Git에 올릴 필요가 없는 파일을 제외하는 역할이다.

## 4. 모듈별 역할

### 4.1 `common`

공통 모듈이다.
앞으로 아래 같은 코드가 여기에 들어간다.

- 공통 예외
- 공통 응답 코드
- 감사 필드
- 금액 객체
- 공통 유틸

### 4.2 `account-domain`

계좌와 고객의 기준 데이터, 계좌 상태, 현재 잔액과 관련된 코드가 들어간다.

예:

- 고객 엔티티
- 계좌 엔티티
- 계좌 잔액 엔티티
- 계좌 상태 변경 로직

### 4.3 `transaction-domain`

거래 헤더, 거래 엔트리, 원장 반영 구조를 담당한다.

예:

- 거래 엔티티
- 거래 엔트리 엔티티
- 원장 기록 엔티티
- 거래 반영 정책

### 4.4 `transfer-domain`

입금, 출금, 계좌이체 같은 실제 자금 이동 유스케이스를 담당한다.

예:

- 입금 서비스
- 출금 서비스
- 계좌이체 서비스
- 정정 거래 서비스

### 4.5 `interest-domain`

이자 정책 조회, 이자 계산, 이자 반영 흐름을 담당한다.

### 4.6 `channel-api`

외부에서 들어오는 REST API 진입점을 담당한다.

MVC 기준으로 보면 이 모듈에는 주로 아래가 들어간다.

- Controller
- Request DTO
- Response DTO
- 입력 검증

### 4.7 `channel-security`

인증, 인가, 접근 정책 검증, 보안 감사와 관련된 코드가 들어간다.

### 4.8 `information-read`

조회 전용 모델과 읽기 최적화 서비스를 담당한다.

즉, 계정계 원천 데이터를 가공해서 조회를 빠르게 하는 역할이다.

### 4.9 `batch`

자동이체, 이자 배치, 정합성 검증 배치 같은 스케줄 작업을 담당한다.

### 4.10 `bootstrap`

애플리케이션 시작점이다.
실행 가능한 Spring Boot Application 클래스가 여기에 있다.

즉, 다른 모듈이 라이브러리처럼 역할을 나누고, `bootstrap` 이 실제 실행을 담당한다.

## 5. 왜 `bootstrap` 모듈이 따로 필요한가

멀티모듈 구조에서는 모든 모듈이 실행 모듈일 필요가 없다.
오히려 하나의 실행 모듈만 두는 편이 구조를 이해하기 쉽다.

그래서 이번 구조에서는:

- 나머지 모듈은 역할별 라이브러리 모듈
- `bootstrap` 은 실행 모듈

로 분리했다.

이렇게 하면 어떤 코드는 재사용 모듈이고, 어떤 코드는 실제 실행 진입점인지 명확해진다.

## 6. MVC와 이번 구조의 연결

Spring MVC 기준으로 보면 앞으로 구조는 아래처럼 이해하면 된다.

- Controller: 주로 `channel-api`
- Service: `transfer-domain`, `interest-domain`, 일부 `account-domain`
- Repository: `account-domain`, `transaction-domain`, `information-read`
- Domain Model: `account-domain`, `transaction-domain`
- Batch Job: `batch`
- Application 시작점: `bootstrap`

즉, MVC만으로 전체 시스템을 설명하기에는 부족하고, 도메인 분리와 기술 역할 분리를 함께 봐야 한다.

## 7. 이번 단계에서 일부러 아직 하지 않은 것

이번에는 아래 항목은 아직 넣지 않았다.

- 실제 엔티티 클래스
- Repository 인터페이스
- Service 구현
- Controller 구현
- Security 설정
- Batch 설정

이유는 먼저 폴더와 모듈의 자리부터 안정적으로 잡는 것이 우선이기 때문이다.

## 8. 현재 구조를 따라가는 방법

지금은 아래 순서로 보면 이해가 쉽다.

1. `settings.gradle` 에서 전체 모듈 보기
2. 루트 `build.gradle` 에서 공통 빌드 규칙 보기
3. 각 모듈의 `build.gradle` 에서 모듈 의존성 보기
4. `bootstrap` 의 `BankingSystemApplication` 에서 실행 시작점 보기
5. 이후 엔티티와 서비스가 들어오면 모듈별 책임과 연결해서 보기

## 9. 남아 있는 점검 사항

현재 환경에서는 `java -version` 으로 Java 21이 확인되었지만, `gradle` 명령은 설치되어 있지 않았다.
그래서 이번 작업에서는 Gradle 설정 파일과 모듈 구조를 먼저 만들었다.

추후에는 아래 중 하나를 진행하면 된다.

- Gradle Wrapper 추가
- 로컬 Gradle 설치 후 빌드 실행
