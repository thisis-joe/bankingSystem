# 작업 기록

## 1. 작업명

- 코어 뱅킹 상위 아키텍처 계획서 작성

## 2. 이번 작업에서 한 일

- 코어 뱅킹 구조를 계정계, 채널계, 정보계로 분리해 상위 설계를 정리했다.
- 기준 데이터, 현재 상태 데이터, 이력 데이터, 조회 데이터를 구분해 DB 관점을 정리했다.
- 핵심 테이블 후보와 관계 원칙, 거래, 자동이체, 이자 처리 흐름을 문서화했다.
- Spring Boot 모듈형 모놀리식 구조와 각 모듈의 책임을 정리했다.
- 기존 영문 파일명을 한글 파일명으로 변경하고 문서 내부 내용도 한글 기준으로 정리했다.

## 3. 왜 이 작업을 했는지

- 코어 뱅킹은 화면보다 원장, 잔액, 거래 이력의 정합성이 먼저이기 때문이다.
- 이후 DDL, 엔티티, 서비스 계층을 만들 때 기준이 되는 상위 구조가 먼저 필요했다.
- 학습 관점에서도 도메인 분리와 데이터 성격 분리를 먼저 이해해야 이후 파일 구조와 코드를 따라가기 쉽다.
- 문서와 파일명을 한글로 통일해야 이후 후속 작업을 더 쉽게 따라가고 수정할 수 있다.

## 4. 어떻게 작업했는지

- 시스템을 계정계, 채널계, 정보계로 나누고 각 책임을 분리했다.
- DB를 기능 기준이 아니라 기준 데이터, 현재 상태 데이터, 이력 데이터, 조회 데이터 기준으로 분류했다.
- 거래는 `bank_transaction` 과 `transaction_entry` 로 나누고, 잔액은 `account_balance`, 이력은 `account_ledger` 로 분리하는 방향으로 설계했다.
- Spring Boot 구조는 처음부터 마이크로서비스로 가지 않고 모듈형 모놀리식으로 잡아 트랜잭션 경계를 안정적으로 관리하도록 했다.
- 문서 파일명과 내부 내용을 모두 한글로 바꾸고 작업 기록 체계도 한글 경로로 정리했다.

## 6. 학습 포인트

- Spring Boot에서 모듈을 나누는 이유는 기능 분리보다 책임 경계를 명확히 하기 위함이다.
- MVC 관점에서 컨트롤러는 요청을 받고, 서비스는 유스케이스를 수행하며, 저장소는 DB 접근을 맡는다.
- 코어 뱅킹에서는 테이블을 단순 기능별로 나누기보다 기준 데이터, 상태 데이터, 이력 데이터로 구분하는 것이 중요하다.
- 잔액은 현재 상태이고, 거래 원장과 거래 엔트리가 실제 이력 원천이 된다.
- 자동이체와 이자 계산도 결국 일반 거래와 같은 원장 흐름으로 연결되어야 안정적이다.
- 문서 체계도 학습 도구이므로 파일명과 본문 표현을 일관되게 유지하는 것이 중요하다.
