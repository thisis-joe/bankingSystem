# 작업 기록

## 1. 작업명

- 멱등 처리 로직 추가

## 2. 이번 작업에서 한 일

- 공통 오류 코드에 멱등 충돌 오류를 추가했다.
- `IdempotencyConflictException` 을 추가했다.
- `TransactionIdempotencyResolver` 를 만들어 중복 요청과 충돌 요청을 판별하도록 했다.
- `TransferApplicationService` 에 멱등 확인 흐름을 추가했다.
- 멱등 처리 테스트를 작성했다.
- 이번 작업의 원리와 이유를 설명하는 문서를 작성했다.

## 3. 왜 이 작업을 했는지

- 코어 뱅킹에서는 같은 요청이 두 번 실행되면 금전 사고로 이어질 수 있기 때문이다.
- API가 이미 `requestId`, `Idempotency-Key` 를 받고 있었으므로 실제 멱등 처리를 붙일 시점이었다.
- 빌드 기반이 확보된 뒤 가장 먼저 붙여야 할 운영 안정성 기능이었다.

## 4. 어떻게 작업했는지

- 서비스 시작 시점에 기존 거래 조회를 먼저 하도록 순서를 바꿨다.
- 같은 요청이면 기존 거래를 반환하게 했다.
- 같은 키가 다른 거래를 가리키거나 다른 거래 유형에 재사용되면 충돌 예외를 던지도록 했다.
- 멱등 처리 로직은 별도 클래스로 분리해 서비스가 너무 커지지 않게 했다.

## 5. 어디에 반영했는지

- 멱등 예외: `common/src/main/java/com/bankingsystem/common/exception/IdempotencyConflictException.java`
- 멱등 처리기: `transfer-domain/src/main/java/com/bankingsystem/transfer/application/support/TransactionIdempotencyResolver.java`
- 서비스 반영: `transfer-domain/src/main/java/com/bankingsystem/transfer/application/service/TransferApplicationService.java`
- 테스트: `transfer-domain/src/test/java/com/bankingsystem/transfer/application/support/TransactionIdempotencyResolverTest.java`
- 설명 문서: `docs/10-멱등-처리-설명.md`
- 현재 작업 기록: `docs/작업기록/2026-04-03-11-멱등-처리.md`

## 6. 학습 포인트

- 멱등성은 같은 요청의 재실행을 안전하게 처리하는 성질이다.
- DB 유니크 제약만으로는 기존 성공 결과 재사용까지 해결되지 않는다.
- 멱등 처리는 서비스 가장 앞단에서 검사하는 것이 자연스럽다.
- 같은 키라도 다른 거래 의미라면 충돌로 봐야 한다.
- 중요한 정책 로직은 별도 클래스로 분리하면 읽기 쉽고 테스트하기 좋다.
