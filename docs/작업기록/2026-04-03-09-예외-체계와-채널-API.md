# 작업 기록

## 1. 작업명

- 예외 체계와 채널 API 작성

## 2. 이번 작업에서 한 일

- 공통 오류 코드와 공통 예외 구조를 추가했다.
- 서비스가 공통 업무 예외를 사용하도록 수정했다.
- 서비스 반환용 결과 객체 `TransferResult` 를 추가했다.
- 입금, 출금, 이체 요청 DTO와 응답 DTO를 작성했다.
- 채널 API 컨트롤러를 추가했다.
- 전역 예외 처리기를 추가했다.
- 이번 구조를 설명하는 한글 문서를 작성했다.

## 3. 왜 이 작업을 했는지

- 내부 구조만으로는 외부 요청을 받을 수 없기 때문이다.
- API를 붙이기 전에 예외 체계를 먼저 정리해야 응답 형식이 흔들리지 않는다.
- 엔티티를 직접 응답으로 노출하지 않기 위해 결과 객체와 DTO가 필요했다.

## 4. 어떻게 작업했는지

- `ErrorCode` 와 `BankingException` 을 만들고 구체 예외 클래스를 추가했다.
- 서비스의 기존 일반 예외를 업무 예외로 바꿨다.
- `TransferResult` 를 만들어 서비스 결과를 분리했다.
- `TransactionController` 에서 헤더와 요청 DTO를 받아 Command 객체로 변환하도록 만들었다.
- `GlobalExceptionHandler` 에서 업무 예외, 검증 예외, 일반 예외를 나누어 처리했다.

## 5. 어디에 반영했는지

- 공통 예외: `common/src/main/java/com/bankingsystem/common/exception/`
- 결과 객체: `transfer-domain/src/main/java/com/bankingsystem/transfer/application/result/TransferResult.java`
- API 요청/응답: `channel-api/src/main/java/com/bankingsystem/channel/api/presentation/`
- 컨트롤러: `channel-api/src/main/java/com/bankingsystem/channel/api/presentation/controller/TransactionController.java`
- 전역 예외 처리기: `channel-api/src/main/java/com/bankingsystem/channel/api/presentation/handler/GlobalExceptionHandler.java`
- 설명 문서: `docs/08-예외-체계와-채널-API-설명.md`
- 현재 작업 기록: `docs/작업기록/2026-04-03-09-예외-체계와-채널-API.md`

## 6. 학습 포인트

- 예외 체계는 서비스와 API의 연결 품질에 큰 영향을 준다.
- 결과 객체와 DTO는 엔티티 직접 노출을 막아 준다.
- 컨트롤러는 요청을 받고 서비스를 호출하며 응답으로 바꾸는 경계 역할을 한다.
- 전역 예외 처리기를 쓰면 API 오류 응답을 한곳에서 통일할 수 있다.
- 채널 타입을 Command 에 넣으면 서비스가 더 유연해진다.
