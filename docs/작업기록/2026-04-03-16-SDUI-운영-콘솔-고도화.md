# 작업 기록

## 1. 작업명

- SDUI 운영 콘솔 고도화

## 2. 이번 작업에서 한 일

- SDUI 화면에 10초 주기 자동 새로고침을 추가했다.
- 자동 새로고침 일시정지/재시작 버튼을 추가했다.
- 시스템 상태 요약 블록을 추가했다.
- 배치 실행 현황 표를 추가했다.
- 운영 로그 블록을 추가했다.
- 블록별 레이아웃 폭을 서버가 지정할 수 있도록 `span` 구조를 추가했다.
- 상단 메타 영역에 마지막 갱신 시각과 자동 갱신 상태를 추가했다.
- 기존 다크/화려한 스타일을 정리하고 밝고 단정한 관리 콘솔 스타일로 바꿨다.
- 실제 실행 후 화면 정의 API와 정적 페이지 응답, 자동 새로고침 설정 값까지 확인했다.
- 이번 변경의 원리와 이유를 설명하는 문서를 작성했다.

## 3. 왜 이 작업을 했는지

- 사용자가 이 UI가 실시간성으로 보이지 않고 로그 등 많은 정보가 부족하다고 지적했기 때문이다.
- 운영 화면은 단순 SDUI 데모보다 더 많은 상태 정보와 이력 정보를 한 화면에서 읽을 수 있어야 하기 때문이다.
- 관리 화면은 화려한 디자인보다 오래 보기 편하고 정보 구조가 잘 보이는 것이 더 중요하기 때문이다.

## 4. 어떻게 작업했는지

### 4.1 완전 실시간 대신 폴링 기반 자동 갱신을 택했다

- 10초 주기 자동 새로고침을 붙였다.
- 이 방식은 구조가 단순하고 관리가 쉽기 때문에 현재 단계에 적합하다고 판단했다.

### 4.2 읽기 모델 정보를 더 풍부하게 만들었다

- 상태 요약
- 정합성 경고
- 최근 거래 흐름
- 최근 채널 요청
- 배치 실행 현황
- 운영 로그
- 운영 메모

이렇게 운영에 필요한 정보 축을 더 늘렸다.

### 4.3 서버가 레이아웃도 더 많이 설명하게 만들었다

- 각 블록에 `span` 을 넣어 서버가 폭을 지정할 수 있게 했다.
- 갱신 주기 역시 `refresh.intervalSeconds` 로 내려주게 했다.

즉, 서버가 데이터뿐 아니라 화면 운용 정책까지 더 많이 제어하게 되었다.

### 4.4 디자인은 정리 중심으로 다시 잡았다

- 강한 그라디언트와 장식성 표현을 줄였다.
- 밝은 배경, 흰 패널, 얇은 경계선, 상태색 중심으로 재구성했다.
- 운영자가 오래 봐도 덜 피로한 형태를 우선했다.

## 6. 이번 작업에서 중요했던 판단

### 6.1 실시간성은 관리 가능한 구조로 먼저 가져갔다

- 지금은 WebSocket 이 아니라 폴링이다.
- 복잡성을 늘리기보다 관리 가능하고 이해 가능한 구조를 먼저 만들었다.

### 6.2 정보량은 늘리되 화면은 더 차분하게 만들었다

- 정보는 더 많아졌지만, 디자인은 더 조용하게 정리했다.
- 관리 화면은 시선 자극보다 가독성이 중요하기 때문이다.

### 6.3 서버가 화면 제어를 더 많이 하도록 했다

- 갱신 주기
- 블록 폭
- 컴포넌트 종류

이런 정보까지 서버가 설명하게 만들어 SDUI 성격을 더 강하게 했다.

## 7. 학습 포인트

- 실시간과 자동 갱신은 같은 것이 아니다.
- 운영 화면에서는 폴링 기반 주기 갱신도 충분히 유효한 전략이다.
- SDUI는 데이터뿐 아니라 화면 배치와 갱신 규칙까지 서버가 설명할 수 있다.
- 관리 화면은 예쁨보다 안정감, 정돈, 정보 구조가 더 중요하다.
- 로그와 상태를 한 화면에 구조적으로 모으면 운영 판단 속도가 빨라진다.
