# 작업 기록

## 1. 작업명

- 코어 뱅킹 핵심 테이블 DDL 초안 작성

## 2. 이번 작업에서 한 일

- 코어 뱅킹 1차 구현 범위에 필요한 핵심 테이블들을 정리했다.
- 실제 SQL 실행 파일을 `database/ddl/V1__core_banking_core_schema.sql` 로 작성했다.
- 왜 이 테이블들이 필요한지, 어떤 기준으로 나누었는지 설명하는 한글 문서를 작성했다.
- 이후 Spring Boot 엔티티와 서비스 설계로 이어질 수 있도록 PK, FK, 유니크 제약, 체크 제약, 인덱스를 포함했다.

## 3. 왜 이 작업을 했는지

- 아키텍처 문서만으로는 실제 구현을 시작하기 어렵기 때문이다.
- 엔티티, 저장소, 서비스, 테스트를 만들려면 먼저 테이블 구조가 있어야 한다.
- 코어 뱅킹에서는 특히 거래 원장, 현재 잔액, 거래 엔트리의 관계가 먼저 확정되어야 이후 로직이 흔들리지 않는다.

## 4. 어떻게 작업했는지

- 상위 아키텍처 문서를 기준으로 계정계 중심의 1차 구현 범위를 추렸다.
- 이번 단계에서는 모든 테이블을 한 번에 확장하지 않고, 입금, 출금, 이체, 자동이체, 이자, API 추적에 필요한 핵심 테이블만 우선 정의했다.
- SQL은 PostgreSQL 기준으로 작성했다.
- 금액은 `numeric(18, 2)`, 금리는 `numeric(9, 6)`, 시각은 `timestamptz` 로 통일했다.
- 현재 잔액 테이블과 원장 이력 테이블을 분리하고, `bank_transaction` 과 `transaction_entry` 도 분리했다.
- 정보계 반영을 위해 `outbox_event` 테이블도 함께 넣었다.

## 6. 학습 포인트

- DDL은 단순히 테이블 생성문이 아니라 백엔드 구조의 기준점이다.
- PK는 행을 유일하게 식별하고, FK는 테이블 사이의 관계를 강제한다.
- 유니크 제약은 업무 식별자 중복을 막는다.
- 체크 제약은 DB 차원에서 잘못된 상태를 막는다.
- 인덱스는 조회 성능을 위한 구조이며, 자주 조회하는 조건을 기준으로 설계한다.
- 현재 상태 데이터와 이력 데이터를 분리하면 정합성과 조회 성능을 함께 챙길 수 있다.
- Spring Boot의 엔티티 설계는 거의 항상 DDL 설계와 같이 움직인다.
