# 작업 기록 가이드

## 목적

이 프로젝트에서는 구현과 학습을 함께 진행하므로, 모든 주요 작업은 코드 변경과 함께 문서화한다.
기록의 목적은 다음과 같다.

- 어떤 작업이 수행되었는지 빠르게 추적
- 왜 그런 구조와 기술을 선택했는지 이해
- Spring, 백엔드, DB, MVC, 파일 구조를 학습 관점에서 복기
- 이후 후속 작업에서 맥락을 유지

## 기록 원칙

앞으로 수행하는 주요 작업은 가능하면 아래 두 가지를 함께 남긴다.

1. 실제 산출물 변경
2. 해당 변경에 대한 작업 기록 문서 작성

작업 기록에는 최소한 아래 항목을 포함한다.

- 무엇을 작업했는가
- 왜 이 작업이 필요한가
- 어떻게 구현했는가
- 어디에 반영했는가
- 학습 포인트는 무엇인가

## 기록 위치

- 공통 규칙 문서: `docs/작업-기록-가이드.md`
- 작업별 기록 문서: `docs/작업기록/`

권장 파일명 형식:

- `docs/작업기록/2026-04-03-01-코어-뱅킹-아키텍처-계획.md`
- `docs/작업기록/2026-04-03-02-DDL-초안.md`
- `docs/작업기록/2026-04-03-03-모듈-뼈대-구성.md`

## 작업 기록 기본 양식

각 작업 기록은 아래 형식을 기본으로 사용한다.

```md
# 작업 기록

## 1. 작업명

- 예: 코어 뱅킹 상위 아키텍처 계획서 작성

## 2. 이번 작업에서 한 일

- 무엇을 만들었는지
- 어떤 파일을 추가하거나 수정했는지

## 3. 왜 이 작업을 했는지

- 이 작업의 목적
- 전체 구조에서의 위치

## 4. 어떻게 작업했는지

- 설계 방식
- 적용한 구조
- 사용한 Spring, DB, MVC 관점

## 5. 어디에 반영했는지

- 파일 경로
- 모듈 위치
- 계층 위치

## 6. 학습 포인트

- 이번 작업에서 이해해야 할 개념
- 문법, 구조, 패턴 관점 정리

## 7. 다음에 이어서 할 일

- 다음 작업 후보
- 후속 변경 포인트
```

## 문서화 기준

아래 경우에는 반드시 작업 기록을 남긴다.

- 새로운 문서 작성
- 새로운 패키지 또는 모듈 생성
- 엔티티, 테이블, DDL 작성
- API, 컨트롤러, 서비스 추가
- 구조 변경
- 중요한 리팩터링

아래 경우에는 간단 기록 또는 기존 작업 기록 갱신으로 충분할 수 있다.

- 오타 수정
- 주석 수정
- 아주 작은 이름 변경

## 학습 관점에서 같이 설명할 내용

앞으로 작업 기록에는 가능하면 아래 관점도 함께 적는다.

- Spring Boot에서 이 파일의 역할
- MVC 기준에서 어느 계층인지
- DB 테이블이라면 기준 데이터인지, 상태 데이터인지, 이력 데이터인지
- 왜 이 클래스를 컨트롤러, 서비스, 저장소, 도메인에 두는지
- 왜 이 관계를 일대일, 일대다, 다대일로 잡는지

## 앞으로의 작업 방식

앞으로 작업할 때는 가능한 흐름을 아래처럼 맞춘다.

1. 작업 수행
2. 변경 파일 반영
3. 작업 기록 문서 작성 또는 갱신
4. 최종 보고 시 변경 내용과 기록 파일 함께 안내

이 규칙은 이후 후속 작업에도 계속 적용한다.
