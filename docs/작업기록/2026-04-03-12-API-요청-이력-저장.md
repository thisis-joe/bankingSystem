# 작업 기록

## 1. 작업명

- API 요청 이력 저장 구조 추가

## 2. 이번 작업에서 한 일

- 채널 API 요청마다 `traceId` 를 부여하는 필터를 추가했다.
- 요청 완료 시 `api_request_log` 테이블에 이력을 남기는 인터셉터를 추가했다.
- 요청 이력 저장용 JPA 엔티티와 저장소를 만들었다.
- 요청 이력 저장 서비스를 별도 트랜잭션으로 분리했다.
- 성공 응답과 오류 응답에 traceId 가 보이도록 응답 구조를 보강했다.
- 필수 헤더 누락, 잘못된 JSON 요청을 400 계열 오류로 명확히 처리하도록 예외 처리기를 보강했다.
- 멱등 테스트 실행 중 드러난 JUnit 플랫폼 런처 불일치를 수정하고 전체 테스트를 다시 통과시켰다.
- 이번 작업의 원리와 이유를 정리한 설명 문서를 작성했다.

## 3. 왜 이 작업을 했는지

- 채널계는 단순 요청 전달 계층이 아니라 요청 식별과 요청 이력 보존 책임을 가져야 하기 때문이다.
- 코어 뱅킹 운영에서는 성공한 거래뿐 아니라 실패한 요청도 나중에 추적 가능해야 하기 때문이다.
- 멱등 처리만으로는 `요청이 어떻게 끝났는가` 를 설명할 수 없으므로 traceId 와 요청 로그가 추가로 필요했다.
- 이후 인증, 인가, API 클라이언트 식별을 붙이기 전에 요청 추적의 기본 틀을 먼저 세우는 것이 자연스럽다고 판단했다.

## 4. 어떻게 작업했는지

### 4.1 테스트 기반부터 먼저 안정화했다

- `transfer-domain` 테스트 런타임에 `junit-platform-launcher` 를 추가했다.
- `.\gradlew.bat test` 를 다시 실행해 전체 모듈 테스트가 통과하는 기준점을 확보했다.

### 4.2 요청 시작 지점과 종료 지점을 분리해 설계했다

- 요청 시작 지점은 `TraceIdFilter` 로 잡았다.
- 요청 종료 지점은 `ApiRequestLoggingInterceptor.afterCompletion` 으로 잡았다.

이렇게 나눈 이유는 시작 시점에는 traceId 와 시작 시간을 안정적으로 잡을 수 있고, 종료 시점에는 최종 상태 코드와 거래 번호를 함께 기록할 수 있기 때문이다.

### 4.3 컨트롤러는 최소 정보만 넘기도록 했다

- 컨트롤러는 성공 시 생성된 `transactionId` 만 요청 컨텍스트에 바인딩한다.
- 실제 요청 이력 저장은 인터셉터가 담당한다.

즉, 컨트롤러가 로깅 책임까지 모두 떠안지 않도록 구조를 분리했다.

### 4.4 요청 이력 저장은 별도 트랜잭션으로 분리했다

- `ApiRequestLogService` 에 `REQUIRES_NEW` 를 적용했다.

이유는 요청 이력 저장이 본 거래 처리와는 성격이 다른 부가성 작업이기 때문이다.
또한 요청 종료 시점에 저장되므로 독립된 저장 단위로 두는 편이 자연스럽다.

## 6. 이번 작업에서 특히 중요했던 판단

### 6.1 traceId 는 모든 요청에 붙어야 한다

- 거래 성공 여부와 상관없이 요청 단위를 식별할 수 있어야 한다.
- 그래서 컨트롤러보다 앞단인 필터에서 생성하거나 이어받도록 했다.

### 6.2 성공과 실패를 모두 기록해야 한다

- 성공 거래만 기록하면 운영 문제의 절반만 보이게 된다.
- 실패 요청도 같은 방식으로 남겨야 장애 추적이 가능하다.

### 6.3 요청 로그 저장 실패가 본 응답을 다시 망치지 않게 했다

- 인터셉터 내부에서 요청 로그 저장 실패를 잡아 경고 로그로 남기게 했다.
- 현재 단계에서는 본 거래 결과를 우선 보존하는 쪽을 선택했다.

## 7. 학습 포인트

- 필터는 요청의 가장 앞단에서 공통 정보를 심기에 좋다.
- 인터셉터의 `afterCompletion` 은 요청 최종 결과를 기록하기에 적합하다.
- MVC 에서 컨트롤러는 업무 입출력 변환에 집중하고, 공통 관심사는 별도 계층으로 분리하는 편이 좋다.
- 별도 트랜잭션은 부가성 저장 작업을 본 업무와 느슨하게 묶는 데 유용하다.
- 오류 응답에도 추적 식별자를 넣으면 운영과 디버깅이 쉬워진다.
