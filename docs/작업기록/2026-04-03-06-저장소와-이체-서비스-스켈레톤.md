# 작업 기록

## 1. 작업명

- 저장소 인터페이스와 이체 서비스 스켈레톤 작성

## 2. 이번 작업에서 한 일

- 계좌계 저장소 인터페이스를 작성했다.
- 거래계 저장소 인터페이스를 작성했다.
- 입금, 출금, 이체 요청 객체를 작성했다.
- `TransferApplicationService` 를 만들어 응용 서비스 흐름을 스켈레톤으로 정리했다.
- 거래 반영 세부 로직을 위한 `TransactionPostingProcessor` 인터페이스를 추가했다.
- 왜 저장소와 서비스를 나누는지 설명 문서를 작성했다.

## 3. 왜 이 작업을 했는지

- 엔티티만으로는 실제 유스케이스 흐름이 보이지 않기 때문이다.
- 코어 뱅킹에서는 데이터를 읽고 쓰는 책임과 업무 흐름을 조합하는 책임을 분리해야 한다.
- 이후 실제 원장 반영 로직을 붙일 수 있도록 서비스 뼈대를 먼저 만드는 것이 자연스러운 순서다.

## 4. 어떻게 작업했는지

- 저장소는 우선 인터페이스로만 만들고, 인프라 구현은 뒤로 미뤘다.
- 서비스는 `@Transactional` 기준으로 입금, 출금, 이체 메서드를 나누었다.
- 공통 검증은 비공개 메서드로 분리했다.
- 실제 거래 반영은 아직 완성하지 않고 `TransactionPostingProcessor` 로 위임하도록 설계했다.

## 5. 어디에 반영했는지

- 계좌계 저장소: `account-domain/src/main/java/com/bankingsystem/account/domain/repository/`
- 거래계 저장소: `transaction-domain/src/main/java/com/bankingsystem/transaction/domain/repository/`
- 요청 객체와 서비스: `transfer-domain/src/main/java/com/bankingsystem/transfer/application/`
- 설명 문서: `docs/저장소와-이체-서비스-스켈레톤-설명.md`
- 현재 작업 기록: `docs/작업기록/2026-04-03-06-저장소와-이체-서비스-스켈레톤.md`

## 6. 학습 포인트

- Repository 는 저장과 조회, Service 는 업무 흐름 조합을 담당한다.
- 응용 서비스는 여러 도메인 객체와 저장소를 묶어 하나의 유스케이스를 실행한다.
- `@Transactional` 은 이 메서드 안 작업을 하나의 트랜잭션으로 묶는 기준이 된다.
- 이체는 단순히 돈을 빼고 넣는 작업이 아니라 조회, 검증, 거래 생성, 반영의 순서를 가진다.
- 큰 서비스를 만들 때는 세부 반영 로직을 별도 인터페이스로 분리하면 구조가 더 명확해진다.
