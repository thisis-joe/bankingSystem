# API 요청 이력 저장 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 `채널계가 받은 요청을 나중에 다시 설명할 수 있도록` API 요청 이력을 남기는 구조를 만드는 것이다.

이전 단계에서 멱등 처리를 추가하면서 같은 요청이 두 번 실행되지 않도록 막았다.
하지만 실제 운영에서는 거기서 끝나지 않는다.

코어 뱅킹 운영에서 자주 나오는 질문은 아래와 같다.

- 이 요청은 실제로 들어왔는가
- 언제 들어왔는가
- 어떤 경로로 들어왔는가
- 어떤 상태 코드로 끝났는가
- 어떤 거래 번호와 연결되는가
- 장애가 났다면 어떤 요청을 따라가야 하는가

즉, 멱등 처리가 `중복 실행 방지` 라면, 이번 작업은 `운영 추적성 확보` 에 가깝다.

## 2. 왜 이 작업이 지금 필요한가

지금 단계에서 이 작업이 필요한 이유는 다음과 같다.

### 2.1 채널계의 책임을 실제 코드로 드러내야 하기 때문이다

상위 설계에서 채널계는 단순히 HTTP 요청을 받아서 계정계 서비스를 호출하는 계층이 아니다.
채널계는 아래 책임을 가져야 한다.

- 요청 식별
- 요청 추적
- 요청 이력 저장
- 외부 API 호출 흔적 보존
- 오류 응답의 표준화

지금까지는 컨트롤러와 예외 처리기까지는 있었지만, `요청 흔적을 남기는 구조` 는 아직 없었다.

### 2.2 코어 뱅킹에서는 성공한 거래만 중요한 것이 아니기 때문이다

운영 현장에서는 실패한 요청도 중요하다.

예를 들어 아래 상황을 생각할 수 있다.

- 사용자가 이체를 시도했지만 잔액 부족으로 실패
- 필수 헤더가 빠져 요청이 400으로 끝남
- JSON 형식이 잘못되어 요청이 파싱되지 않음
- 서버 내부 예외로 500이 발생함

이 경우 실제 거래는 만들어지지 않을 수 있다.
그래도 채널계에서는 `어떤 요청이 어떤 결과로 끝났는지` 남아 있어야 장애 분석과 감사 대응이 가능하다.

### 2.3 멱등 처리와 함께 봐야 요청 단위 추적이 완성되기 때문이다

이전 단계에서 `requestId`, `Idempotency-Key` 로 중복 요청을 판별하도록 만들었다.
이번 단계에서는 여기에 `traceId` 와 `API 요청 이력` 을 연결했다.

이렇게 되면 요청을 아래 두 관점으로 추적할 수 있다.

- 업무 관점: 이 요청이 어떤 거래를 만들었는가
- 운영 관점: 이 요청이 어떤 HTTP 흐름으로 들어와 어떤 상태로 끝났는가

## 3. 이번에 설계한 흐름의 큰 그림

이번 작업의 흐름은 아래와 같다.

1. 요청이 들어오면 `TraceIdFilter` 가 가장 먼저 실행된다.
2. `traceId` 와 요청 시작 시각을 요청 컨텍스트에 저장한다.
3. 컨트롤러가 실제 입금, 출금, 이체 서비스를 호출한다.
4. 거래가 성공하면 컨트롤러가 `transactionId` 를 요청 컨텍스트에 기록한다.
5. 요청이 끝날 때 `ApiRequestLoggingInterceptor` 가 실행된다.
6. 최종 HTTP 상태 코드, 요청 경로, 메서드, `requestId`, `idempotencyKey`, `traceId`, `transactionId` 를 모아 DB에 저장한다.

중요한 점은 `요청 시작` 과 `요청 종료` 를 다른 지점에서 잡았다는 것이다.

- 시작 시점: 필터
- 종료 시점: 인터셉터

이 설계를 선택한 이유는 아래에서 자세히 설명한다.

## 4. 왜 TraceIdFilter 가 먼저 필요한가

### 4.1 traceId 는 거래 ID 와 다른 개념이기 때문이다

`transactionId` 는 거래가 실제로 만들어져야 생긴다.
반면 `traceId` 는 거래 성공 여부와 관계없이 모든 요청에 붙일 수 있다.

즉:

- 거래가 성공하면 `traceId` 와 `transactionId` 둘 다 존재
- 거래가 실패하면 `traceId` 는 존재하지만 `transactionId` 는 없을 수 있음

그래서 추적의 시작점은 `transactionId` 가 아니라 `traceId` 여야 한다.

### 4.2 필터는 컨트롤러보다 먼저 실행되기 때문이다

`TraceIdFilter` 는 컨트롤러보다 먼저 실행된다.
그래서 아래 같은 경우도 traceId 를 부여할 수 있다.

- 헤더 검증 실패
- 본문 파싱 실패
- 예외 처리기에서 끝난 요청

만약 traceId 생성 로직을 컨트롤러에만 넣으면, 컨트롤러에 도달하지 못한 실패 요청은 추적하기 어렵다.

### 4.3 응답에도 같은 traceId 를 실어 줄 수 있기 때문이다

필터에서 `X-Trace-Id` 응답 헤더를 내려주도록 했다.
이렇게 하면 클라이언트와 서버가 같은 식별자를 공유할 수 있다.

즉, 나중에 문제가 생겼을 때 다음처럼 연결할 수 있다.

- 사용자가 받은 응답의 traceId
- 서버 로그의 traceId
- DB의 `api_request_log.trace_id`

## 5. 왜 요청 종료 이력은 인터셉터에서 저장했는가

### 5.1 종료 시점의 상태 코드를 알아야 하기 때문이다

API 요청 이력에는 `response_status` 가 들어간다.
이 값은 요청이 끝나기 전에는 확정되지 않는다.

예를 들어 요청이 들어왔을 때는 모두 200처럼 보일 수 있지만, 실제로는 아래처럼 끝날 수 있다.

- 200 성공
- 400 검증 실패
- 404 자원 없음
- 409 멱등 충돌
- 500 내부 오류

그래서 요청 이력 저장은 컨트롤러 시작 시점보다 `요청이 모두 끝난 시점` 이 더 적합하다.

### 5.2 인터셉터의 afterCompletion 은 성공과 실패를 모두 본다

`afterCompletion` 은 정상 응답 후에도 호출되고, 예외 처리 후에도 호출된다.
즉, 성공/실패를 나누어 별도 코드 경로를 많이 만들지 않아도 요청 종료 지점을 한 군데에서 모을 수 있다.

이 구조의 장점은 다음과 같다.

- 컨트롤러에 로깅 코드가 과도하게 퍼지지 않는다
- 실패 요청도 빠짐없이 같은 구조로 기록할 수 있다
- 채널계의 공통 관심사를 한 곳에 모을 수 있다

## 6. 왜 컨트롤러는 transactionId 만 요청 컨텍스트에 남겼는가

이번 설계에서 컨트롤러의 책임은 아주 제한적으로 두었다.

컨트롤러가 하는 일:

- 요청을 서비스 명령 객체로 변환
- 서비스 실행
- 성공 시 `transactionId` 를 요청 컨텍스트에 기록
- 응답 DTO 변환

컨트롤러가 하지 않는 일:

- DB 로그 직접 저장
- traceId 생성
- 종료 상태 코드 계산

이렇게 나눈 이유는 MVC 와 계층 책임을 흐리지 않기 위해서다.

컨트롤러가 모든 로깅 책임까지 직접 가지면 다음 문제가 생긴다.

- 모든 API 메서드마다 중복 코드 증가
- 실패 흐름 처리 누락 가능성 증가
- 채널 공통 정책이 여러 컨트롤러로 흩어짐

그래서 컨트롤러는 `업무 결과 중 인터셉터가 알아야 하는 최소 정보`, 즉 `transactionId` 만 전달하도록 했다.

## 7. 왜 요청 이력 저장은 별도 트랜잭션으로 분리했는가

이번 작업에서 중요한 설계 포인트 중 하나가 `REQUIRES_NEW` 이다.

`ApiRequestLogService` 는 별도 트랜잭션으로 동작하도록 만들었다.

### 7.1 본 거래 처리와 요청 이력 저장은 성격이 다르기 때문이다

본 거래 처리:

- 계좌 잔액 반영
- 거래 엔트리 생성
- 원장 생성

요청 이력 저장:

- 채널계 감사/추적용 기록

둘 다 중요하지만, 역할이 다르다.
요청 이력 저장까지 본 거래와 완전히 같은 트랜잭션에 묶으면, 추적용 부가 작업이 본 업무를 끌어내릴 수 있다.

### 7.2 요청 종료 시점에는 이미 본 업무 트랜잭션이 끝났을 가능성이 크기 때문이다

인터셉터의 `afterCompletion` 은 요청이 마무리되는 단계에서 호출된다.
따라서 이 시점의 로그 저장은 별도 단위로 처리하는 편이 더 자연스럽다.

### 7.3 로그 저장 실패가 사용자 응답을 다시 깨뜨리지 않도록 하기 위해서다

인터셉터는 로그 저장 실패를 잡아서 경고 로그만 남기도록 했다.
이 선택은 `요청 이력 실패 때문에 이미 계산된 사용자 응답을 다시 망가뜨리지 않는다` 는 의도다.

이 판단은 상황에 따라 달라질 수 있다.
금융권 실제 운영에서는 감사 로그 실패를 매우 심각하게 다룰 수 있다.
하지만 현재 학습용 1차 구현에서는 아래 균형을 선택했다.

- 본 거래 성공/실패 결과는 유지
- 요청 이력 저장 실패는 운영 로그로 알림
- 이후 필요하면 재시도나 outbox 구조로 발전 가능

## 8. 이번에 추가한 주요 코드와 역할

### 8.1 `ChannelApiConstants`

역할:

- 헤더 이름 상수 정의
- 요청 속성 이름 정의
- 현재 채널 ID 상수 정의

왜 필요한가:

- `"X-Request-Id"` 같은 문자열이 여러 파일에 흩어지는 것을 막기 위해서다.
- 오타 가능성을 줄이고 의미를 한곳에서 관리할 수 있다.

### 8.2 `RequestAuditSupport`

역할:

- traceId 조회
- 요청 시작 시각 조회
- requestId, idempotencyKey 조회
- transactionId 바인딩/조회

왜 필요한가:

- 필터, 컨트롤러, 예외 처리기, 인터셉터가 같은 규칙으로 요청 정보를 읽도록 만들기 위해서다.
- 요청 정보 해석 규칙이 한 곳에 모이면 변경이 쉬워진다.

### 8.3 `TraceIdFilter`

역할:

- `X-Trace-Id` 를 읽거나 새로 생성
- 요청 시작 시각 저장
- 응답 헤더에 traceId 설정
- MDC 에 traceId 저장

원리:

- 요청이 시스템에 들어오는 가장 앞단에서 추적 식별자를 붙인다.

### 8.4 `ApiRequestLoggingInterceptor`

역할:

- 요청 완료 시 최종 정보를 모아 `api_request_log` 에 저장

원리:

- 종료 시점의 최종 상태 코드와 실제 `transactionId` 를 함께 기록한다.

### 8.5 `ApiRequestLog`

역할:

- `api_request_log` 테이블과 매핑되는 JPA 엔티티

주의점:

- 이 엔티티는 `BaseEntity` 를 상속하지 않았다.
- 이유는 현재 DDL 이 `created_at` 만 가지고 있고 `updated_at` 은 없기 때문이다.

즉, 공통 기반 클래스를 무조건 재사용하는 것이 아니라 `테이블 구조에 맞는 매핑` 을 우선했다.

### 8.6 `GlobalExceptionHandler` 와 응답 DTO 수정

역할:

- 오류 응답에도 traceId 를 포함
- 필수 헤더 누락과 JSON 파싱 오류를 400 계열로 명확히 응답

이유:

- 실패 요청도 추적 식별자를 가져야 운영자가 같은 요청을 찾기 쉽다.
- 잘못된 요청을 500으로 처리하면 문제 원인을 왜곡하게 된다.

## 9. requestId 가 없을 때 왜 대체 값을 만드는가

`api_request_log.request_id` 는 DDL 상 `not null` 이다.
그런데 현실에서는 잘못된 요청이 들어올 수 있다.

예를 들어:

- `X-Request-Id` 헤더 누락
- API 스펙을 지키지 않은 외부 호출

이때도 요청 이력을 남기고 싶기 때문에, `RequestAuditSupport` 는 `requestId` 가 없으면 `AUTO-{traceId}` 형태의 대체 값을 만든다.

이 선택의 의미는 아래와 같다.

- 정상 요청: 클라이언트가 준 requestId 사용
- 비정상 요청: 시스템이 만든 대체 requestId 사용

즉, 스펙 위반 요청이어도 추적 단절을 만들지 않겠다는 의도다.

## 10. 현재 설계의 가정과 한계

이번 구현은 1차 버전이므로 몇 가지 가정이 있다.

### 10.1 `OPEN_API_CHANNEL_ID = 1`

현재는 `channel` 기준 데이터가 아직 코드로 모델링되지 않았기 때문에, `OPEN_API` 채널이 DB에 `1` 번으로 존재한다는 가정을 두었다.

즉, 이후에는 아래 중 하나로 발전해야 한다.

- `channel` 기준 데이터 시드 추가
- `ChannelType -> channelId` 매핑 리졸버 추가
- 채널 기준 엔티티 도입

### 10.2 `api_client_id` 는 아직 비워 둔다

현재는 인증/인가 구조를 아직 만들지 않았기 때문에 어떤 API 클라이언트가 호출했는지까지는 연결하지 않았다.
추후 `channel-security` 모듈이 실제로 붙으면 연결할 수 있다.

### 10.3 응답 본문 자체는 저장하지 않는다

지금은 요청 메타데이터와 응답 상태 중심으로만 기록한다.
응답 전문 저장은 개인정보, 보안, 저장 공간, 마스킹 정책까지 같이 고려해야 하므로 다음 단계의 별도 설계가 필요하다.

## 11. 이번 단계에서 얻은 구조적 이점

이번 작업으로 아래 구조가 생겼다.

- 모든 거래 API 요청은 traceId 를 가진다
- 성공/실패 요청 모두 DB 이력으로 남길 수 있다
- 성공 요청은 `transactionId` 와 연결된다
- 오류 응답에도 traceId 가 포함된다
- 요청 추적 책임이 채널계에 명확히 위치한다

즉, 이제 채널계는 단순한 컨트롤러 묶음이 아니라 `입구에서 요청을 식별하고, 끝에서 이력을 남기는 계층` 으로 한 단계 더 구체화되었다.

## 12. 학습 포인트

- 필터는 컨트롤러 전에 실행되므로 공통 추적 식별자 부여에 적합하다.
- 인터셉터의 `afterCompletion` 은 요청 최종 결과를 수집하기 좋다.
- 컨트롤러는 공통 로깅보다는 업무 입출력 변환 책임에 집중하는 편이 구조상 깔끔하다.
- 부가성 로그 저장은 별도 트랜잭션으로 분리하면 본 업무 흐름과 결합도를 낮출 수 있다.
- 성공 요청뿐 아니라 실패 요청도 남겨야 운영 추적이 완성된다.

## 13. 다음 작업 후보

이번 단계 다음으로 자연스러운 작업은 아래 중 하나다.

1. `channel` 기준 데이터와 `api_client` 기준 데이터 모델링
2. 인증/인가 구조 추가 후 `api_client_id` 연결
3. API 요청 이력 조회용 정보계 읽기 모델 추가
4. 통합 테스트로 필터, 인터셉터, 예외 응답 흐름 검증

현재 우선순위로는 `channel 기준 데이터와 인증 구조` 가 가장 자연스럽다.
이유는 지금 만든 요청 이력 구조가 더 완전해지려면 `누가 호출했는가` 와 `어떤 채널인가` 가 실제 기준 데이터와 연결되어야 하기 때문이다.
