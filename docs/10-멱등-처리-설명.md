# 멱등 처리 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 같은 요청이 여러 번 들어와도 거래가 한 번만 반영되도록 멱등 처리를 추가하는 것이다.

코어 뱅킹에서는 멱등성이 매우 중요하다.
이유는 현실에서 아래 상황이 자주 발생하기 때문이다.

- 사용자가 버튼을 두 번 누름
- 모바일 네트워크 재전송
- 클라이언트 타임아웃 후 같은 요청 재호출
- 게이트웨이 재시도

이때 멱등 처리가 없으면 아래 같은 사고가 날 수 있다.

- 입금이 두 번 반영됨
- 출금이 두 번 빠짐
- 같은 이체가 두 번 실행됨

즉, 멱등성은 편의 기능이 아니라 금융 시스템의 안전장치다.

## 2. 멱등성이란 무엇인가

멱등성은 같은 요청을 여러 번 보내더라도 결과가 한 번 실행한 것과 같아야 한다는 성질이다.

예를 들어 같은 이체 요청을 두 번 보내더라도:

- 첫 번째 요청에서 이미 성공했다면
- 두 번째 요청은 새 거래를 만들지 않고
- 기존 거래 결과를 그대로 돌려줘야 한다.

즉, 핵심은 `같은 요청을 다시 받았을 때 새 돈 이동을 만들지 않는 것` 이다.

## 3. 이번에 어떤 방식으로 구현했는가

이번 구현은 서비스 계층에서 먼저 중복 요청을 검사하는 방식이다.

사용한 기준은 두 가지다.

- `requestId`
- `Idempotency-Key`

현재 흐름은 아래와 같다.

1. 요청이 서비스에 들어온다.
2. `requestId`, `Idempotency-Key` 로 기존 거래를 찾는다.
3. 같은 거래가 이미 있으면 새 거래를 만들지 않는다.
4. 기존 거래 결과를 그대로 반환한다.
5. 없으면 새 거래를 생성하고 정상 흐름을 진행한다.

## 4. 왜 DB 유니크 제약만으로는 부족한가

이미 `bank_transaction` 테이블에는 `request_id`, `idempotency_key` 유니크 제약이 있다.
그럼 왜 서비스 로직이 또 필요한지 궁금할 수 있다.

이유는 다음과 같다.

### 4.1 유니크 제약은 막아 주기만 한다

DB 유니크 제약은 중복 저장을 막을 수는 있지만, 클라이언트에게 기존 성공 결과를 돌려주지는 못한다.

즉:

- DB만 쓰면 보통 예외가 터진다.
- 서비스 멱등 처리를 쓰면 기존 결과를 재사용할 수 있다.

### 4.2 서비스 계층이 의도를 더 잘 표현한다

멱등성은 단순 저장 중복 방지가 아니라 업무 의미다.
그래서 서비스 계층에서 먼저 검사하는 편이 더 읽기 쉽고 유지보수하기 좋다.

## 5. 이번에 만든 핵심 클래스

### 5.1 `TransactionIdempotencyResolver`

이 클래스가 멱등 처리의 핵심이다.

역할:

- `requestId` 로 기존 거래 조회
- `Idempotency-Key` 로 기존 거래 조회
- 둘이 같은 거래를 가리키는지 확인
- 기존 거래 유형과 새 요청 거래 유형이 같은지 확인
- 문제가 없으면 기존 거래를 반환

즉, 이 클래스는 "이번 요청이 정말 같은 요청인지" 를 판별하는 역할을 한다.

## 6. 왜 충돌 검사가 필요한가

같은 키가 들어왔다고 해서 무조건 기존 결과를 돌려주면 안 되는 경우도 있다.

예를 들어:

- 같은 `Idempotency-Key` 를 입금 요청과 이체 요청에 같이 써버린 경우
- `requestId` 는 한 거래를 가리키고, `Idempotency-Key` 는 다른 거래를 가리키는 경우

이런 상황은 같은 요청의 재시도가 아니라 잘못된 키 재사용이다.
그래서 이번에는 이런 경우를 `IdempotencyConflictException` 으로 막도록 했다.

즉, 멱등 처리에는 두 가지가 있다.

- 정상 중복 요청: 기존 결과 반환
- 잘못된 키 충돌: 오류로 차단

## 7. 서비스는 어떻게 바뀌었는가

이전에는 서비스가 바로 금액 검증과 계좌 조회를 시작했다.
이번에는 각 메서드 시작 부분에 멱등 확인이 먼저 들어갔다.

예를 들어 입금 흐름은 이제 아래처럼 된다.

1. `requestId`, `Idempotency-Key` 로 기존 거래 조회
2. 있으면 기존 결과 반환
3. 없으면 금액 검증
4. 계좌 조회
5. 잔액 잠금 조회
6. 거래 생성
7. 엔트리, 원장, 잔액 반영
8. 결과 반환

즉, 중복 요청은 가장 앞단에서 걸러야 한다.

## 8. 왜 거래 유형도 같이 비교하는가

같은 멱등 키라도 다른 종류의 요청이면 같은 요청으로 보면 안 된다.

예:

- 기존 거래: `DEPOSIT`
- 새 요청: `TRANSFER`

이 경우는 재시도가 아니라 잘못된 키 재사용이다.
그래서 기존 거래가 있어도 거래 유형이 다르면 충돌 예외를 던진다.

이 원칙이 중요한 이유는 금융 거래에서 "같은 키" 보다 "같은 의미의 요청" 이 더 중요하기 때문이다.

## 9. 테스트는 무엇을 검증하는가

이번에는 멱등 처리 전용 테스트도 추가했다.

검증한 항목:

- 같은 `requestId` 와 `Idempotency-Key` 면 기존 거래 반환
- 같은 멱등 키를 다른 거래 유형에 재사용하면 충돌 예외 발생
- `requestId` 와 멱등 키가 서로 다른 거래를 가리키면 충돌 예외 발생

이 테스트가 중요한 이유는 멱등 처리는 눈으로 보기에는 단순해 보여도, 실제로는 충돌 조건이 섬세하기 때문이다.

## 10. 이번 구현의 한계

이번 멱등 처리는 1차 구현이다.
아직 남아 있는 부분도 있다.

### 10.1 요청 본문 해시 비교는 없다

지금은 거래 유형 중심으로만 충돌을 본다.
같은 키에 다른 금액을 넣어 보낸 경우까지 완전히 구분하지는 않는다.

### 10.2 실패 거래 재처리 정책은 없다

현재는 기존 거래가 있으면 그대로 재사용하는 방향이다.
추후에는 실패 상태 거래를 어떻게 다룰지 정책이 더 필요할 수 있다.

### 10.3 API 요청 로그와 아직 직접 연결되지는 않았다

다음 단계에서 API 사용 이력 저장을 붙이면 멱등 정보와 요청 로그를 같이 추적할 수 있다.

## 11. 이번 단계에서 얻은 것

이번 작업으로 얻은 가장 중요한 변화는 아래다.

- 같은 요청이 다시 들어와도 새 거래를 만들지 않는 구조
- 잘못된 멱등 키 재사용을 막는 구조
- 멱등 처리를 서비스 맨 앞단에서 읽을 수 있는 구조

즉, 이제 코어 뱅킹의 가장 중요한 운영 안정성 요소 중 하나를 코드에 반영한 상태다.
