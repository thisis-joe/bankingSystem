# SDUI 운영 콘솔 고도화 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 기존 SDUI 관리자 화면을 `더 운영적인 화면` 으로 바꾸는 것이다.

이전 화면은 SDUI 개념을 이해하기 위한 첫 예제에 가까웠다.
즉, 아래를 보여 주는 데 초점이 있었다.

- 서버가 JSON으로 화면 구조를 내려준다.
- 브라우저가 그 JSON을 렌더링한다.

하지만 실제 관리 화면 관점에서는 부족한 점이 있었다.

- 자동 갱신이 없어 스냅샷 느낌이 강했다.
- 운영 로그와 배치 상태가 충분히 보이지 않았다.
- 시스템 상태를 요약해서 읽는 구조가 약했다.
- 화면이 관제판처럼 다소 화려해 장시간 보는 관리 화면으로는 부담이 있었다.

그래서 이번에는 다음 방향으로 고도화했다.

1. `실시간에 가까운 주기적 갱신` 추가
2. `로그, 배치, 시스템 상태` 정보 추가
3. `더 구조적인 운영 화면` 으로 정리
4. `지나치게 화려하지 않은 관리 콘솔 디자인` 으로 변경

## 2. 이 화면은 지금 실시간인가

완전한 의미의 실시간 푸시 화면은 아니다.
대신 `10초 주기 폴링 기반의 준실시간 운영 콘솔` 로 바뀌었다.

즉, 현재 방식은 아래와 같다.

- 브라우저가 10초마다 화면 정의 JSON을 다시 요청한다.
- 서버가 최신 스냅샷을 다시 내려준다.
- 화면이 그 JSON으로 다시 렌더링된다.

이 방식의 장점은 다음과 같다.

- 구현이 단순하다
- 관리와 디버깅이 쉽다
- WebSocket, SSE 없이도 운영 화면으로 충분히 쓸 수 있다
- SDUI 구조를 흐리지 않는다

왜 이 방식을 먼저 선택했는가:

사용자가 `관리 편의성` 을 가장 중요하게 두었기 때문이다.
운영 콘솔은 화려한 실시간성보다 `안정적이고 이해 가능한 갱신 구조` 가 더 중요할 때가 많다.

즉, 지금 단계에서는 아래 균형을 택했다.

- 너무 무거운 실시간 기술은 아직 도입하지 않음
- 대신 폴링으로 현재 상태를 계속 다시 읽음
- 구조는 단순하게 유지

## 3. 왜 폴링이 관리 화면에 잘 맞는가

운영 화면에서 진짜 중요한 것은 매 프레임 바뀌는 애니메이션이 아니다.
중요한 것은 아래다.

- 지금 상태가 충분히 최근인가
- 갱신이 예측 가능한가
- 장애가 나도 원인을 추적하기 쉬운가
- 화면 로직이 복잡해지지 않는가

폴링은 이런 요구에 비교적 잘 맞는다.

특히 이번 프로젝트처럼 SDUI 학습과 구조 이해가 중요한 상황에서는 아래 장점이 크다.

- 요청 흐름이 단순하다
- 브라우저 개발자도구 Network 탭에서 쉽게 따라갈 수 있다
- 서버가 내려주는 JSON 스냅샷을 직접 확인할 수 있다
- 나중에 진짜 실시간 푸시로 바꾸더라도 현재 구조를 기반으로 확장 가능하다

## 4. 이번에 어떤 정보가 추가되었는가

이번 고도화의 핵심은 `더 많은 정보를 한 페이지에서 구조적으로 볼 수 있게 만든 것` 이다.

추가/강화된 영역은 아래와 같다.

### 4.1 시스템 상태 요약

새로 추가된 `status-grid` 블록은 아래 상태를 한눈에 보여 준다.

- 계정계 원장
- 채널 API
- 자동이체 배치
- 정보계 읽기 모델
- 보안 설정
- DB 연결

이 블록의 목적은 운영자가 페이지를 열자마자 `어느 영역이 정상이고 어느 영역이 주의 상태인지` 빠르게 읽게 하는 것이다.

### 4.2 배치 실행 현황

기존 화면에는 배치 정보가 거의 없었다.
이번에는 아래 정보를 표로 추가했다.

- 배치명
- 상태
- 마지막 실행 시각
- 다음 실행 시각
- 메모

코어 뱅킹은 배치가 중요하므로, 관리 화면에서 이 정보가 보이는 것이 자연스럽다.

### 4.3 운영 로그

이번에는 `log-list` 블록을 추가했다.

보여 주는 정보:

- 로그 레벨
- 분류
- 메시지
- 발생 시각
- Trace ID

이 영역은 단순 예쁜 리스트가 아니라, 운영자가 최근 이슈를 빠르게 스캔하는 목적이다.

### 4.4 자동 갱신 상태 표시

상단 메타 영역에 아래를 추가했다.

- 마지막 갱신 시각
- 자동 갱신 상태
- 자동 새로고침 일시정지 버튼

이 정보는 운영 화면에서 생각보다 중요하다.
화면이 자동으로 갱신되고 있는지 모르면, 사용자는 지금 보고 있는 값이 최신인지 확신하기 어렵기 때문이다.

## 5. 이번에 서버 JSON 구조는 어떻게 바뀌었는가

이전보다 SDUI 화면 정의가 더 운영용 구조를 담게 되었다.

대표적으로 추가된 내용은 아래다.

- `refresh`
- 블록별 `span`
- 새로운 `status-grid` 컴포넌트
- 새로운 `log-list` 컴포넌트

예를 들면:

```json
{
  "refresh": {
    "enabled": true,
    "intervalSeconds": 10
  }
}
```

이 값은 서버가 단순 데이터뿐 아니라 `화면 갱신 정책` 도 일부 설명하기 시작했다는 뜻이다.

또한 블록마다 `span` 값을 넣어 레이아웃 폭까지 서버가 제어할 수 있게 했다.

즉, 이제 서버는 아래를 같이 결정한다.

- 어떤 블록을 보여 줄 것인가
- 어떤 순서로 보여 줄 것인가
- 그 블록이 얼마나 넓게 보일 것인가
- 얼마나 자주 갱신할 것인가

이 점이 SDUI의 장점이 잘 드러나는 부분이다.

## 6. 왜 `span` 이 관리 편의성에 도움이 되는가

이전에는 클라이언트 CSS가 컴포넌트 종류별로 대략적인 너비를 정하는 방식이었다.
하지만 관리 화면은 상황에 따라 다음 요구가 생긴다.

- 로그 블록을 더 좁게 하고 표를 넓게 하고 싶다
- 어떤 권한에서는 배치 표를 크게 보고 싶다
- 어떤 환경에서는 상태 블록을 전체 폭으로 보고 싶다

이런 요구를 감당하려면, 레이아웃도 서버가 어느 정도 설명하는 편이 관리가 쉽다.

그래서 이번에는 `block.span` 을 도입했다.
클라이언트는 이 값을 읽어 grid-column 을 결정한다.

즉, 브라우저가 임의로 판단하는 것이 아니라 서버가 `이 블록은 12칸, 이 블록은 7칸, 이 블록은 5칸` 이라고 알려 주는 구조다.

## 7. 디자인을 왜 단순하게 바꿨는가

사용자는 이번에 `지나치게 화려하지 않고 깔끔하게`, 그리고 `관리가 편한 것` 을 원했다.

그래서 디자인을 아래 방향으로 바꿨다.

- 강한 다크 그라디언트 제거
- 밝은 배경과 흰 패널 중심
- 색은 상태 표시용으로만 절제해서 사용
- 긴 애니메이션과 장식성 표현 최소화
- 표, 카드, 로그, 상태 블록을 읽기 쉬운 간격으로 정리

즉, 시선을 끄는 화면보다 `오래 봐도 피곤하지 않은 운영 콘솔` 을 목표로 했다.

이건 관리자 화면에서 아주 중요한 기준이다.

- 예쁜 화면보다 읽기 쉬운 화면
- 화려한 장식보다 정보 밀도와 정돈
- 개성보다 일관성과 유지보수성

## 8. 브라우저는 어떻게 바뀌었는가

이번 브라우저 렌더러 고도화 포인트는 아래다.

### 8.1 자동 새로고침

`app.js` 가 `refresh.intervalSeconds` 를 읽어서 주기적 재요청을 한다.

즉, 갱신 주기도 하드코딩이 아니라 서버 정의를 따르는 구조에 가까워졌다.

### 8.2 새 컴포넌트 추가

렌더러가 새로 지원하는 컴포넌트:

- `status-grid`
- `log-list`

즉, SDUI는 컴포넌트를 조금씩 늘려 가며 범용 렌더러를 키워 가는 방식이라는 점이 더 잘 드러난다.

### 8.3 자동 갱신 토글

관리 화면에서는 때로 자동 갱신을 잠시 멈추고 현재 화면을 읽고 싶을 수 있다.
그래서 자동 갱신 일시정지/재시작 버튼을 추가했다.

이것도 관리 편의성을 고려한 선택이다.

## 9. 이번 단계에서 구조적으로 더 좋아진 점

이번 고도화 이후 아래 개선이 생겼다.

- 단순 예제 화면에서 실제 운영 콘솔에 가까운 구조로 발전했다
- 상태, 로그, 배치, 요청 흐름이 한 화면에 함께 보인다
- 자동 새로고침으로 최신성을 더 쉽게 유지할 수 있다
- 화면이 훨씬 덜 화려하고 더 읽기 쉬워졌다
- 서버가 레이아웃 폭과 갱신 주기까지 설명하기 시작했다

즉, 이제 SDUI가 단순한 "JSON 화면 실험" 이 아니라 `운영 화면 제어 방식` 으로 보이기 시작한다.

## 10. 현재 한계

이번 화면은 여전히 학습용 예제다.

### 10.1 진짜 푸시 실시간은 아니다

현재는 폴링 기반이다.
즉, 서버가 먼저 밀어주는 방식은 아니다.

### 10.2 로그와 상태는 샘플 읽기 모델이다

현재는 실제 DB나 로그 저장소에서 가져오는 대신 샘플 데이터를 읽기 모델 서비스에서 만들고 있다.
이후에는 실제 요청 로그, 배치 실행 테이블, 원장 검증 결과와 연결할 수 있다.

### 10.3 권한별 화면 분기는 아직 없다

운영자 역할에 따라 다른 블록을 내려주는 SDUI의 강점은 다음 단계에서 더 확장할 수 있다.

## 11. 학습 포인트

- 운영 화면에서 실시간성은 항상 WebSocket 이어야 하는 것은 아니다.
- 관리 편의성과 구조 단순성을 우선하면 폴링이 좋은 선택일 수 있다.
- SDUI는 데이터뿐 아니라 레이아웃과 갱신 정책까지 서버가 설명할 수 있다.
- 화려한 UI보다 상태, 로그, 배치, 요청 흐름을 읽기 쉬운 구조로 배치하는 것이 관리 화면에 더 적합하다.
- 범용 렌더러는 컴포넌트를 조금씩 늘려 가면서 성장시킬 수 있다.

## 12. 다음 작업 후보

이제 다음으로 자연스러운 작업은 아래 중 하나다.

1. 실제 `api_request_log` 데이터를 읽기 모델과 연결
2. 배치 실행 결과를 실제 테이블과 연결
3. 권한에 따라 다른 블록을 내려주는 SDUI 정책 추가
4. SSE 기반 실시간 푸시 버전 추가

현재 우선순위로는 `실제 요청 로그와 배치 결과 연결` 이 가장 자연스럽다.
이유는 지금 화면이 구조는 충분히 좋아졌고, 다음에는 정보를 실제 데이터로 채우는 단계가 가장 큰 가치가 있기 때문이다.
