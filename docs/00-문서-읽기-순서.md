# 문서 읽기 순서

## 1. 이 문서의 목적

이 문서는 현재 프로젝트 문서를 어떤 순서로 읽어야 하는지 한눈에 보여주기 위한 안내서다.
이전에는 파일명만으로 문서 역할을 구분해야 해서, 처음 따라오는 사람이 어느 문서부터 읽어야 하는지 헷갈릴 수 있었다.
그래서 이제 설명 문서는 번호형 파일명으로 정리하고, 이 문서에서 추천 읽기 순서를 같이 안내한다.

## 2. 먼저 보면 좋은 참고자료

프로젝트를 바로 실행해서 SDUI 화면과 JSON 화면 정의를 확인하고 싶다면 아래 문서를 먼저 보면 된다.

## 4. 문서별 의미

### 3.1 `01-코어-뱅킹-아키텍처.md`

프로젝트의 가장 상위 설계 문서다.
계정계, 채널계, 정보계의 역할과 경계, 데이터 분류 원칙, 거래 흐름, 모듈 구조의 큰 방향을 설명한다.

### 3.2 `02-핵심-테이블-DDL-초안.md`

상위 아키텍처를 실제 DB 구조로 내린 문서다.
어떤 테이블이 필요한지, 왜 필요한지, 어떤 제약과 인덱스를 두는지 설명한다.

### 3.3 `03-스프링부트-멀티모듈-뼈대-설명.md`

프로젝트 코드 구조를 어떻게 나눴는지 설명한다.
모듈별 책임, 루트 Gradle 설정, 실행 모듈과 라이브러리 모듈의 차이를 이해할 수 있다.

### 3.4 `04-공통-감사필드와-계좌계-엔티티-설명.md`

공통 기반 클래스와 계좌계 엔티티가 어떻게 만들어졌는지 설명한다.
고객, 상품, 계좌, 계좌 잔액 구조를 이해하는 단계다.

### 3.5 `05-거래계-엔티티-설명.md`

거래 헤더, 거래 엔트리, 계좌 원장 구조를 설명한다.
코어 뱅킹에서 왜 원장 구조가 중요한지 이해하는 핵심 문서다.

### 3.6 `06-저장소와-이체-서비스-스켈레톤-설명.md`

Repository 와 Service 의 역할 차이, 입금, 출금, 이체의 응용 서비스 흐름을 설명한다.

### 3.7 `07-JPA-구현체와-거래-반영-처리기-설명.md`

Spring Data JPA 구현체와 실제 거래 반영 흐름을 설명한다.
잔액 잠금, 엔트리 생성, 원장 생성, 잔액 저장의 연결을 확인할 수 있다.

### 3.8 `08-예외-체계와-채널-API-설명.md`

공통 예외 체계, 결과 객체, 요청과 응답 DTO, 채널 API 컨트롤러, 전역 예외 처리기를 설명한다.
즉, 내부 도메인 구조가 외부 HTTP API와 연결되는 지점을 이해하는 단계다.

### 3.9 `09-그래들-래퍼와-빌드-검증-설명.md`

Gradle Wrapper 를 왜 추가했는지, 실제 빌드 검증이 왜 중요한지, 현재 프로젝트가 어떤 상태까지 검증되었는지를 설명한다.
즉, 이제부터는 기능 추가 전에 빌드 가능한 프로젝트라는 기준을 확보했다는 점을 이해하는 단계다.

### 3.10 `10-멱등-처리-설명.md`

같은 요청이 여러 번 들어와도 거래가 한 번만 반영되도록 하는 멱등 처리의 원리와 구현 방식을 설명한다.
중복 요청 재사용과 잘못된 키 충돌을 어떻게 구분하는지도 이해할 수 있다.

### 3.11 `11-API-요청-이력-저장-설명.md`

채널계에서 traceId 를 만들고, 요청 종료 시 API 요청 이력을 저장하는 구조를 설명한다.
왜 필터와 인터셉터를 나누어 사용했는지, 왜 요청 이력 저장을 별도 트랜잭션으로 분리했는지도 이해할 수 있다.

### 3.12 `12-채널-기준-데이터와-API-클라이언트-설명.md`

채널과 API 클라이언트를 기준 데이터로 모델링하고, 요청 이력이 더 이상 하드코딩된 채널 ID 에 의존하지 않도록 바꾼 구조를 설명한다.
식별과 인증의 차이, 왜 `channel-security` 모듈에 두었는지도 함께 이해할 수 있다.

### 3.13 `13-SDUI-관리자-화면-설명.md`

서버가 화면 구조를 JSON으로 내려주고 브라우저가 이를 렌더링하는 SDUI 개념과, 왜 관리자 화면이 SDUI와 잘 맞는지를 설명한다.
이번 프로젝트에서 `information-read`, `channel-api`, `bootstrap/static` 이 어떤 역할로 나뉘는지도 이해할 수 있다.

### 3.14 `14-SDUI-운영-콘솔-고도화-설명.md`

기존 SDUI 예제 화면을 자동 갱신, 상태 요약, 배치 현황, 운영 로그가 포함된 운영 콘솔 형태로 고도화한 내용을 설명한다.
왜 완전 실시간 대신 폴링을 먼저 택했는지, 왜 디자인을 더 차분하게 바꿨는지도 이해할 수 있다.

### 3.15 `15-통합-ERD-데이터-흐름-API-명세서.md`

현재 프로젝트의 ERD, 데이터 흐름, API 명세를 한 문서로 묶은 통합 문서다.
현재 구현된 범위와 DDL만 준비된 범위를 같이 구분해서 볼 수 있고, 전체 구조를 한 번에 잡고 싶을 때 가장 먼저 참고하기 좋다.

## 5. 작업기록은 어떻게 읽으면 되는가

설명 문서를 다 읽은 뒤에는 `docs/작업기록` 폴더를 보면 된다.
작업기록은 시간순으로 쌓이며, 언제 어떤 작업을 했는지 추적하는 용도다.

추천 순서는 아래와 같다.

1. `docs/작업기록/00-작업기록-목차.md`
2. `docs/작업기록/00-작업-기록-가이드.md`
3. `docs/작업기록/01-작업기록-양식.md`
4. 날짜와 번호가 들어간 작업기록 파일들

## 6. 문서 읽는 방법 추천

프로젝트를 처음부터 이해하고 싶다면 아래 순서가 가장 좋다.

1. 상위 구조 이해
2. DB 구조 이해
3. 코드 모듈 구조 이해
4. 엔티티 구조 이해
5. 서비스 흐름 이해
6. 실제 반영 구현 이해
7. 채널 API와 예외 응답 구조 이해
8. 빌드와 검증 기반 이해
9. 멱등 처리와 중복 요청 방지 원리 이해
10. API 요청 추적과 요청 이력 저장 원리 이해
11. 채널 기준 데이터와 API 클라이언트 식별 구조 이해
12. SDUI 개념과 관리자 화면 구조 이해
13. SDUI 운영 콘솔 고도화 방향 이해
14. 통합 ERD, 데이터 흐름, API 명세 한 번에 이해하기
15. 작업기록으로 변경 히스토리 따라가기

## 7. 앞으로 문서를 추가하는 규칙

앞으로 설명 문서는 아래 형식을 따른다.

- `08-...설명.md`
- `09-...설명.md`
- `10-...설명.md`
- `11-...설명.md`
- `12-...설명.md`
- `13-...설명.md`
- `14-...설명.md`
- `15-...설명.md`

즉, 읽는 순서가 파일명에 드러나도록 계속 번호를 붙인다.

작업기록은 기존처럼 날짜와 작업 순번을 유지한다.
이유는 작업기록은 읽기 순서보다 작업 시점 추적이 더 중요하기 때문이다.
