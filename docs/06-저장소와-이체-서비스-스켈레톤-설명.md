# 저장소와 이체 서비스 스켈레톤 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 지금까지 만든 엔티티들을 실제 유스케이스 흐름으로 연결할 수 있도록 저장소 인터페이스와 응용 서비스 스켈레톤을 만드는 것이다.

이번 단계에서 중요한 것은 완성된 기능 구현이 아니라, 아래 두 가지를 명확하게 분리하는 것이다.

- 데이터를 어디에서 읽고 저장할 것인가
- 업무 흐름을 어떤 서비스가 조합할 것인가

## 2. 왜 저장소와 서비스를 나누는가

Spring 백엔드 학습에서 가장 자주 헷갈리는 부분 중 하나가 `Repository` 와 `Service` 의 역할 차이다.

쉽게 말하면:

- Repository 는 데이터를 가져오고 저장하는 역할
- Service 는 업무 순서를 조합하고 검증하는 역할

코어 뱅킹에서는 이 차이가 더 중요하다.
왜냐하면 이체 한 번에도 아래 순서가 있기 때문이다.

1. 계좌 조회
2. 잔액 조회 및 잠금
3. 금액 검증
4. 거래 헤더 생성
5. 거래 엔트리와 원장 반영
6. 거래 완료 처리

이 중 Repository 는 조회와 저장만 담당하고, 이 순서를 조합하는 책임은 Service 가 가져야 한다.

## 3. 이번에 만든 저장소 인터페이스

### 3.1 계좌계 저장소

- `CustomerRepository`
- `ProductRepository`
- `AccountRepository`
- `AccountBalanceRepository`

이 저장소들은 아직 JPA 구현체가 아니라 `도메인 관점의 인터페이스` 다.
즉, 나중에 인프라 계층에서 Spring Data JPA 구현체를 붙일 수 있도록 계약만 먼저 만든 것이다.

특히 `AccountBalanceRepository` 에는 아래 메서드를 넣었다.

- `findByAccountId`
- `findByAccountIdForUpdate`

여기서 `findByAccountIdForUpdate` 는 이체나 출금처럼 동시성 제어가 필요한 작업을 위해 잠금 조회를 의도한 메서드다.

## 4. 이번에 만든 거래계 저장소

- `BankTransactionRepository`
- `TransactionEntryRepository`
- `AccountLedgerRepository`

이 저장소들의 의미는 다음과 같다.

- 거래 헤더 저장
- 거래 엔트리 여러 건 저장
- 계좌 원장 여러 건 저장

즉, 서비스는 이 저장소들을 조합해 한 번의 거래 흐름을 완성하게 된다.

## 5. 왜 서비스 이름이 `TransferApplicationService` 인가

이번 서비스는 단순히 이체만 처리하는 서비스가 아니라 입금, 출금, 이체를 모두 묶은 응용 서비스다.

여기서 `ApplicationService` 라는 이름을 쓴 이유는, 이 클래스가:

- 컨트롤러도 아니고
- 순수 엔티티도 아니고
- 저장소도 아니며
- 여러 도메인 요소를 조합해서 하나의 유스케이스를 실행하는 역할

이기 때문이다.

즉, 응용 계층의 서비스라는 뜻이다.

## 6. 이번 서비스가 하는 일

`TransferApplicationService` 는 아래 흐름을 스켈레톤으로 담고 있다.

## 7. 왜 `TransactionPostingProcessor` 를 따로 뒀는가

이번 단계에서는 입금, 출금, 이체의 흐름은 만들었지만, 실제 거래 엔트리와 원장을 만드는 세부 반영 엔진은 아직 구현하지 않았다.

그래서 그 역할을 `TransactionPostingProcessor` 라는 인터페이스로 분리했다.

이렇게 나누는 이유는 다음과 같다.

- 응용 서비스는 전체 순서를 담당한다.
- 반영 처리기는 거래 엔트리, 원장, 잔액 갱신 같은 세부 반영을 담당한다.

즉, 서비스는 오케스트레이션을 맡고, 반영 처리기는 실제 포스팅을 맡도록 책임을 분리한 것이다.

## 8. MVC 관점에서 지금 만든 것의 위치

- Controller: 아직 없음
- Service: `TransferApplicationService`
- Repository: 저장소 인터페이스들
- Model: 기존 엔티티들

즉, 이제 막 MVC와 도메인 구조가 연결되기 시작한 단계다.

## 9. 이번 단계에서 일부러 아직 하지 않은 것

이번에는 아래는 아직 구현하지 않았다.

- Spring Data JPA 구현체
- 실제 거래 엔트리 저장 로직
- 실제 원장 저장 로직
- 잔액 갱신 로직
- 예외 체계 정리
- 컨트롤러와 DTO

이유는 먼저 구조와 역할을 분리한 뒤에, 그 위에 실제 구현을 얹는 것이 학습과 유지보수에 더 유리하기 때문이다.
