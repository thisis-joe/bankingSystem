# 코어 뱅킹 아키텍처

## 1. 문서 목적

이 문서는 Spring Boot 기반 코어 뱅킹 시스템의 1차 구현 기준이 되는 상위 아키텍처를 정의한다.
핵심 목표는 화면 중심 개발이 아니라 구조적 안정성, 거래 정합성, 감사 가능성, 유지보수 가능한 도메인 분리를 확보하는 것이다.

시스템은 다음 세 영역으로 나눈다.

- 계정계: 잔액, 원장, 이체, 이자, 수수료를 관리하는 진실 원천 시스템
- 채널계: 외부 요청 접수, 인증, 인가, 한도, API 사용 이력을 관리하는 계층
- 정보계: 조회, 통계, 리포트, 운영 대시보드를 위한 읽기 전용 최적화 계층

## 2. 핵심 설계 원칙

### 2.1 반드시 지켜야 하는 원칙

- 금전 상태 변경은 반드시 변경 이력으로 남겨야 한다.
- 현재 잔액은 운영용 현재 상태이며, 거래 원장이 실제 기준 데이터다.
- 정정이 필요할 때는 기존 이력을 덮어쓰지 않고 반대 거래 또는 조정 거래로 처리한다.
- 채널계는 계정계 데이터를 직접 변경하지 않는다.
- 정보계는 조회 최적화와 분석을 담당하며 원천 데이터는 계정계에 둔다.
- 외부 요청으로 발생한 거래는 모두 요청 식별자와 멱등 키로 추적 가능해야 한다.

### 2.2 데이터 분류 원칙

DB 데이터는 기능만으로 나누지 않고 성격에 따라 구분한다.

- 기준 데이터: 고객, 계좌, 상품, 정책, 채널, 코드
- 현재 상태 데이터: 현재 잔액, 계좌 상태, 다음 자동이체 예정 시각, 현재 사용량
- 이력 데이터: 거래 원장, 거래 상세, 자동이체 실행 이력, 이자 반영 이력, API 호출 로그
- 조회 데이터: 통계, 거래내역 조회 모델, 대시보드 집계 데이터

## 3. 도메인 경계

### 3.1 계정계

주요 책임:

- 고객과 계좌 관계 관리
- 계좌 개설, 변경, 해지 상태 관리
- 입금, 출금, 이체, 취소, 정정
- 현재 잔액 갱신
- 불변 거래 원장 기록
- 자동이체 등록과 실행
- 이자 계산과 이자 반영
- 수수료 부과

특징:

- 가장 강한 정합성이 필요하다.
- ACID 트랜잭션 중심으로 설계한다.
- 쓰기 권한을 가장 엄격하게 제한한다.

### 3.2 채널계

주요 책임:

- 외부 API 요청 접수
- 세션 또는 토큰 검증
- 인증과 인가
- 채널별 한도와 정책 검사
- 요청 형식 검증과 멱등 키 접수
- API 접근 로그와 감사 이력 저장

특징:

- 업무의 실제 처리 주체가 아니라 진입 통제와 흐름 조정 역할을 맡는다.
- 계정계 원장을 직접 제어하지 않는다.
- 보안과 추적성이 중요하다.

### 3.3 정보계

주요 책임:

- 거래내역 조회 모델 구성
- 고객 활동 조회 화면 지원
- 일별, 월별 통계 생성
- 운영 리포트와 대시보드 지원
- 조회 성능 최적화

특징:

- 일부 조회는 최종 일관성으로도 허용 가능하다.
- 비정규화 구조를 허용한다.
- 계정계 원천 데이터와 이벤트를 기반으로 재생성 가능해야 한다.

## 4. 권장 시스템 형태

### 4.1 1단계 권장 구조

초기 구현은 마이크로서비스가 아니라 모듈형 모놀리식이 적합하다.
금융 거래는 트랜잭션 경계를 강하게 보호해야 하므로, 처음부터 서비스 분산을 하기보다 하나의 배포 단위 안에서 모듈 경계를 명확히 두는 편이 안정적이다.

권장 모듈:

- 공통 모듈
- 계좌 도메인 모듈
- 거래 도메인 모듈
- 이체 도메인 모듈
- 이자 도메인 모듈
- 채널 API 모듈
- 채널 보안 모듈
- 정보 조회 모듈
- 배치 모듈
- 부트스트랩 모듈

### 4.2 모듈 내부 계층

각 모듈은 아래 계층을 기본으로 둔다.

- 표현 계층: 컨트롤러, 요청과 응답 객체
- 응용 계층: 유스케이스, 트랜잭션 경계, 서비스 흐름 제어
- 도메인 계층: 엔티티, 애그리거트, 도메인 서비스, 저장소 인터페이스
- 인프라 계층: JPA 구현체, 이벤트 발행기, 외부 시스템 연동

핵심 원칙은 비즈니스 규칙을 컨트롤러나 SQL 스크립트에 두지 않고 응용 계층과 도메인 계층에 둔다는 점이다.

## 6. 데이터 관계 원칙

### 6.1 기준 원천 원칙

- `account` 는 계좌 식별의 기준 데이터다.
- `account_balance` 는 현재 상태 캐시이며 법적 원천이 아니다.
- `bank_transaction` 과 `transaction_entry` 가 실제 거래 반영의 기준이다.
- `account_ledger` 는 계좌 중심의 불변 이력 스트림이다.

### 6.2 참조 원칙

- 기준 데이터는 정책에 따라 수정 가능하다.
- 이력 데이터는 특별한 법적 요구가 없는 한 물리적으로 수정하지 않는다.
- 이력 테이블에는 당시 의미를 보존하기 위해 금리, 수수료, 계좌번호 같은 스냅샷 값을 함께 저장할 수 있다.

### 6.3 정합성 원칙

하나의 금전 거래가 성공적으로 반영될 때는 같은 트랜잭션 안에서 다음이 함께 처리되어야 한다.

- `bank_transaction` 생성
- 하나 이상의 `transaction_entry` 생성
- 관련 `account_ledger` 생성
- `account_balance` 갱신

이 중 하나라도 실패하면 전체 반영을 롤백한다.

## 7. 거래 흐름

### 7.1 입금

1. 채널계가 요청과 인증을 검증한다.
2. 채널계가 요청 식별자, 추적 식별자, 멱등 키를 부여한다.
3. 계정계 응용 서비스가 계좌와 잔액을 조회하고 필요한 락을 잡는다.
4. 시스템이 `bank_transaction` 을 생성한다.
5. 시스템이 입금 `transaction_entry` 를 생성한다.
6. 시스템이 `account_ledger` 를 기록한다.
7. 시스템이 `account_balance` 를 갱신한다.
8. 커밋한다.
9. 정보계 반영용 아웃박스 이벤트를 기록한다.

### 7.2 계좌이체

1. 채널계가 이체 권한과 한도를 검증한다.
2. 계정계가 출금 계좌와 입금 계좌를 조회한다.
3. 출금 계좌 잔액을 락하고 잔액을 검증한다.
4. 하나의 이체 `bank_transaction` 을 생성한다.
5. 출금과 입금 `transaction_entry` 를 생성한다.
6. 두 계좌의 `account_ledger` 를 생성한다.
7. 양쪽 `account_balance` 를 갱신한다.
8. 커밋한다.
9. 정보계가 반영 이벤트를 소비한다.

### 7.3 자동이체

1. 배치가 실행 대상 `auto_transfer_schedule` 을 조회한다.
2. 각 대상마다 `auto_transfer_execution` 시도 이력을 만든다.
3. 실제 자금 이동은 일반 이체 유스케이스를 재사용한다.
4. 결과를 `auto_transfer_execution` 에 기록한다.
5. 다음 실행 일정을 갱신한다.

원칙:

- 자동이체는 별도 잔액 변경 경로를 만들지 않고 일반 이체 엔진을 재사용해야 한다.

### 7.4 이자 처리

1. 배치가 `interest_calculation_batch` 를 생성한다.
2. 대상 계좌별로 `interest_accrual_history` 를 기록한다.
3. 반영 단계에서 실제 이자 `bank_transaction` 을 생성한다.
4. 원장과 잔액을 함께 갱신한다.
5. `interest_posting_history` 로 계산과 반영을 연결한다.

원칙:

- 계산된 이자와 실제 반영된 이자는 분리 추적 가능해야 한다.
