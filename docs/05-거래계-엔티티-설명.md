# 거래계 엔티티 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 계좌계 기준 데이터 위에 실제 거래 흐름을 올릴 수 있도록 거래계 핵심 엔티티를 만드는 것이다.
코어 뱅킹에서는 입금, 출금, 이체 같은 기능을 단순 서비스 메서드로만 보면 안 되고, 반드시 거래 헤더와 거래 반영 이력 구조로 이해해야 한다.

이번에 만든 범위는 아래와 같다.

- 거래 유형과 상태 enum
- 채널 유형 enum
- 거래 엔트리 유형 enum
- 원장 유형 enum
- 거래 헤더 엔티티
- 거래 엔트리 엔티티
- 계좌 원장 엔티티

## 2. 왜 거래계 엔티티가 필요한가

계좌 엔티티만 있으면 계좌 자체는 표현할 수 있지만, 자금이 어떻게 움직였는지는 표현할 수 없다.
코어 뱅킹에서 정말 중요한 것은 현재 잔액보다도 거래 이력과 원장이다.

그래서 다음 세 가지가 필요하다.

- 하나의 업무 거래를 표현하는 구조
- 그 거래가 각 계좌에 어떤 영향을 주었는지 표현하는 구조
- 계좌 기준으로 시간순 이력을 빠르게 따라갈 수 있는 구조

이번 작업은 바로 그 세 가지를 코드로 옮긴 것이다.

## 3. `BankTransaction` 이 하는 일

`BankTransaction` 은 하나의 업무 거래를 표현한다.

예를 들면 아래가 모두 하나의 `BankTransaction` 이 될 수 있다.

- 입금 1건
- 출금 1건
- 계좌이체 1건
- 이자 반영 1건
- 수수료 부과 1건

주요 필드:

- 거래 유형
- 거래 상태
- 요청 식별자
- 멱등 키
- 채널 유형
- 업무 일자
- 발생 시각
- 반영 시각
- 설명

즉, 이 엔티티는 거래의 업무적 정체성을 표현한다.

## 4. 왜 `TransactionEntry` 가 따로 필요한가

업무 거래 한 건이 실제 계좌 반영은 여러 줄로 나뉠 수 있기 때문이다.

예를 들어 계좌이체는 업무적으로는 한 건이지만, 실제 자금 이동은 최소 두 줄이다.

- 출금 계좌 엔트리
- 입금 계좌 엔트리

그래서 `TransactionEntry` 를 따로 두었다.

주요 필드:

- 연결된 거래 헤더
- 영향을 받은 계좌
- 차변/대변 구분
- 금액
- 통화 코드
- 반영 후 잔액
- 거래 내 순번

즉, `TransactionEntry` 는 실제 자금 반영의 최소 단위다.

## 5. 왜 `AccountLedger` 가 또 필요한가

`TransactionEntry` 만 있어도 거래 반영 자체는 표현할 수 있다.
하지만 계좌별 조회와 감사 추적을 생각하면 계좌 중심 원장 구조가 별도로 있는 편이 훨씬 유리하다.

`AccountLedger` 의 역할은 아래와 같다.

- 특정 계좌 기준으로 거래 이력을 빠르게 따라가기
- 계좌 입장에서 입금인지 출금인지 더 명확하게 표현하기
- 감사 및 운영 조회에 적합한 형태 만들기

즉, `TransactionEntry` 는 거래 중심이고, `AccountLedger` 는 계좌 중심이다.

## 6. enum 을 왜 이렇게 나누었는가

### 6.1 `TransactionType`

거래가 어떤 업무 유형인지 표현한다.

예:

- 입금
- 출금
- 이체
- 이자 반영
- 수수료 부과
- 반대 거래
- 조정 거래

### 6.2 `TransactionStatus`

거래가 현재 어떤 상태인지 표현한다.

예:

- 요청됨
- 반영 완료
- 실패
- 반대 처리됨

### 6.3 `ChannelType`

어떤 채널에서 거래가 들어왔는지 표현한다.

예:

- 창구
- 인터넷뱅킹
- 모바일뱅킹
- ATM
- 배치
- 오픈 API

### 6.4 `EntryType`

거래 엔트리의 방향을 표현한다.

- 차변
- 대변

### 6.5 `LedgerType`

계좌 원장 관점에서 어떤 성격의 이력인지 표현한다.

예:

- 입금
- 출금
- 이체 출금
- 이체 입금
- 이자
- 수수료
- 반대 거래

이렇게 나누면 서로 다른 개념이 하나의 문자열 필드에 섞이지 않게 할 수 있다.

## 7. JPA 관계를 어떻게 이해해야 하는가

이번에 만든 핵심 관계는 아래와 같다.

- `BankTransaction` 1 : N `TransactionEntry`
- `BankTransaction` 1 : N `AccountLedger`
- `TransactionEntry` N : 1 `Account`
- `AccountLedger` N : 1 `Account`
- `AccountLedger` N : 1 `TransactionEntry`

이 구조를 보면 아래 해석이 가능하다.

- 하나의 거래는 여러 반영 줄을 가질 수 있다.
- 하나의 거래는 여러 원장 줄을 가질 수 있다.
- 한 계좌는 여러 거래 엔트리와 원장 이력을 가진다.

## 8. 계좌이체를 예로 들면

계좌이체 1건이 들어오면 개념상 아래처럼 된다.

1. `BankTransaction` 1건 생성
2. `TransactionEntry` 2건 생성
3. `AccountLedger` 2건 생성
4. 출금 계좌의 `AccountBalance` 갱신
5. 입금 계좌의 `AccountBalance` 갱신

이 구조를 먼저 이해하면 나중에 서비스 로직이 왜 길어지는지, 왜 트랜잭션이 중요한지 이해하기 쉬워진다.

## 9. 이번 단계에서 일부러 아직 하지 않은 것

이번에는 아래는 아직 넣지 않았다.

- 저장소 인터페이스
- 입금, 출금, 이체 서비스
- 거래 검증 정책
- 멱등 처리 서비스
- 원장 반영 서비스

이유는 먼저 거래계 모델 자체를 안정적으로 세우는 것이 우선이기 때문이다.
