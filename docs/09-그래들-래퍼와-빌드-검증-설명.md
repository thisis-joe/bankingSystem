# 그래들 래퍼와 빌드 검증 설명

## 1. 이번 작업의 목적

이번 작업의 목적은 지금까지 만든 구조와 코드가 실제로 컴파일 가능한 프로젝트인지 검증할 수 있는 기반을 만드는 것이다.

이전까지는 문서, 엔티티, 저장소, 서비스, API까지 계속 쌓아 왔지만, 한 가지 중요한 문제가 있었다.

- `gradle` 명령이 로컬 환경에 없어서 실제 빌드를 돌려보지 못했다.

즉, 구조는 좋아 보여도 실제로는 깨져 있을 수 있는 상태였다.

그래서 이번에는 기능을 더 추가하기 전에 먼저 아래를 해결했다.

- Gradle Wrapper 추가
- 로컬 빌드 실행 가능 상태 만들기
- 실제 컴파일과 테스트 태스크 실행

## 2. 왜 이 작업이 지금 꼭 필요했는가

기능을 더 추가하는 것도 중요하지만, 현재 상태에서 더 중요한 것은 `검증 가능한 개발 흐름` 을 만드는 것이었다.

이 단계가 필요한 이유는 다음과 같다.

### 2.1 빌드가 안 되면 구조가 맞는지 알 수 없다

설계가 아무리 좋아도 컴파일이 안 되면 실제 프로젝트로 이어질 수 없다.

### 2.2 이후 변경을 안전하게 하려면 기준점이 있어야 한다

앞으로 엔티티를 바꾸고, 서비스 로직을 늘리고, API를 확장할수록 실수 가능성이 커진다.
이때 빌드가 한 번이라도 돌아가는 상태를 만들어 두면 이후 변경에서 무엇이 깨졌는지 빨리 찾을 수 있다.

### 2.3 학습 관점에서도 매우 중요하다

백엔드 학습에서는 코드 작성만큼이나 아래를 이해하는 것이 중요하다.

- 프로젝트가 어떻게 빌드되는지
- 의존성이 어떻게 내려오는지
- 멀티모듈이 실제로 어떻게 묶이는지
- 내가 만든 코드가 진짜 프로젝트로 연결되는지

즉, 이번 작업은 기능 개발이라기보다 `개발 기반 공사` 에 가깝다.

## 3. Gradle Wrapper 가 무엇인가

Gradle Wrapper 는 프로젝트에 포함되는 실행 스크립트와 설정 파일이다.

대표 파일:

- `gradlew`
- `gradlew.bat`
- `gradle/wrapper/gradle-wrapper.jar`
- `gradle/wrapper/gradle-wrapper.properties`

이 파일들이 있으면, 개발자 PC에 Gradle이 별도로 설치되어 있지 않아도 프로젝트가 지정한 Gradle 버전으로 빌드를 실행할 수 있다.

즉:

- 예전 방식: 각자 PC에 Gradle 설치 필요
- Wrapper 방식: 프로젝트가 필요한 Gradle 버전을 스스로 준비

그래서 팀 프로젝트에서는 보통 Wrapper 를 같이 커밋한다.

## 4. 이번에 실제로 한 일

### 4.1 Gradle Wrapper 생성

프로젝트에 Gradle Wrapper 파일을 추가했다.
이제부터는 로컬에 Gradle이 설치되어 있지 않아도 아래 명령으로 빌드할 수 있다.

```powershell
.\gradlew.bat test
```

### 4.2 실제 빌드 실행

Wrapper 를 만든 뒤 실제로 `test` 태스크를 실행했다.

결과:

- 전체 모듈 컴파일 성공
- 테스트 소스가 없는 모듈은 `NO-SOURCE`
- 최종 결과는 `BUILD SUCCESSFUL`

즉, 현재까지 만든 멀티모듈 구조와 코드가 최소한 컴파일 가능한 상태라는 점을 확인했다.

## 5. 이번 검증으로 확인된 것

이번 빌드 성공이 의미하는 것은 아래와 같다.

### 5.1 모듈 의존성이 맞다

- `common`
- `account-domain`
- `transaction-domain`
- `transfer-domain`
- `channel-api`
- `bootstrap`

등의 모듈 관계가 실제로 컴파일 가능한 상태라는 뜻이다.

### 5.2 패키지 구조와 import 관계가 맞다

지금까지 만든 엔티티, 저장소, 서비스, 컨트롤러, 예외 구조가 서로 연결되며 컴파일 오류 없이 묶였다는 뜻이다.

### 5.3 Spring Boot 기반 뼈대가 실제 프로젝트 형태로 서 있다

이제 더 이상 "문서만 있는 설계" 가 아니라, 실제 빌드 가능한 백엔드 프로젝트로 넘어온 상태다.

## 6. 왜 Wrapper 가 특히 학습에 좋은가

학습 관점에서 Wrapper 는 아주 중요하다.

이유는 다음과 같다.

- 환경 의존성을 줄여 준다.
- 프로젝트 실행 방식이 파일로 명확히 남는다.
- 나중에 팀원이나 다른 PC에서도 같은 방식으로 실행 가능하다.
- 빌드 실패와 성공을 직접 보며 구조를 확인할 수 있다.

즉, Wrapper 는 단순 편의 기능이 아니라 재현 가능한 개발 환경의 시작점이다.

## 7. 이번에 새로 생긴 주요 파일

- `gradlew`
- `gradlew.bat`
- `gradle/wrapper/gradle-wrapper.jar`
- `gradle/wrapper/gradle-wrapper.properties`

그리고 `.temp/` 는 임시 다운로드 경로였기 때문에 `.gitignore` 에 제외 대상으로 추가했다.

## 8. 임시 폴더가 남아 있는 이유

Gradle Wrapper 생성과 빌드 실행 뒤에 `.temp` 폴더를 정리하려고 했지만, 일부 Gradle 파일이 프로세스에 의해 잠겨 있어 즉시 삭제되지 않았다.

이건 개발 도중 가끔 생기는 현상이다.
중요한 점은 아래 두 가지다.

- 프로젝트 빌드 자체는 성공했다.
- `.temp/` 는 Git 제외 대상으로 처리했다.

즉, 버전 관리에는 영향이 없고, 이후 잠금이 풀리면 정리 가능하다.

## 9. 이번 단계에서 얻은 기준점

이번 작업 이후부터는 아래 기준을 가질 수 있다.

1. 기능 추가 후 `.\gradlew.bat test` 로 최소 컴파일 확인
2. 구조 변경 후 다시 빌드 확인
3. 빌드가 깨지면 바로 그 시점에서 수정

이 기준이 생기면 다음 작업이 훨씬 안전해진다.

## 10. 지금 시점에서 다음 작업은 무엇이 좋은가

이제 빌드 기반이 생겼으므로, 다시 기능 확장으로 돌아갈 수 있다.
가장 자연스러운 다음 작업은 아래다.

1. 멱등 처리 로직 추가
2. API 사용 이력 저장
3. 채널 인증과 인가 구조 추가
4. 테스트 코드 작성

특히 다음 우선순위는 `멱등 처리 로직` 이 가장 적절하다.
이유는 이미 API가 `X-Request-Id`, `Idempotency-Key` 를 받고 있고, 코어 뱅킹에서는 중복 요청 방지가 매우 중요하기 때문이다.

## 11. 학습 포인트

- Wrapper 는 프로젝트가 필요한 Gradle 버전을 스스로 관리하게 해 준다.
- 빌드 성공은 단순 메시지가 아니라 모듈 구조와 코드 연결이 실제로 맞는다는 증거다.
- 멀티모듈 프로젝트는 문서만이 아니라 실제 빌드로도 검증해야 한다.
- 기능 개발과 별개로 빌드 기반을 먼저 잡는 것이 장기적으로 더 효율적이다.
